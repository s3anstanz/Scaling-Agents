Lesson 11 Week 3 · Systems ~16 min 10–25 agents

Work as a dependency graph

Before you add agents, you need to know which pieces of work can happen at the same time. For a migration, the answer is already written down in the import statements. This lesson turns those imports into a plan that ten or more agents can follow.

Part oneWhy coding resists parallel agents

In Week 2 you ran three to five agents at once. It went well because you picked the modules. ops/invert.py, ops/flip.py and ops/crop.py all depend on core/image.py, which was already ported, and on nothing else. They had no reason to wait for each other.

That luck does not hold for a whole codebase. Anthropic's post on its multi-agent research system reports that a lead agent with parallel subagents beat a single agent by 90.2% on their internal research eval. The same post warns that multi-agent setups fit poorly when agents need shared context or have many dependencies between them, and it says plainly that this includes most coding tasks.

The reason is easy to see on Kestrel. Ask an agent to port core/image.py before core/color.ts exists and it has two bad options. It can invent the TypeScript API of color (it will guess wrong, and the real port will disagree later), or it can stall. Either way, adding agents made things worse.

The way out is to stop treating "the codebase" as one blob. Make every dependency explicit, and parallel work becomes a scheduling question you can answer with a script. That is what this week is about. Lesson 11 finds the graph. Lesson 12 adds contracts so agents share context through files instead of conversation. Lesson 14 adds isolation so they stop writing over each other. Those three fixes line up with the three things the research post said coding was missing.

Part twoFour words: DAG, wave, width, critical path

A DAG is a directed acyclic graph. Each module is a node. Draw an arrow from A to B when B imports A, which means A must be ported first. "Acyclic" means you can never follow arrows and end up where you started. A cycle would be a real problem: two modules that each need the other first. Kestrel has none, and python scripts/deps.py prints its graph as an adjacency list.

A topological order is any ordering of the modules where every module comes after everything it imports. One agent porting one module at a time just needs any topological order. Week 1 followed one without naming it.

A wave (also called a layer) groups modules by how deep their dependencies go. Wave L0 holds modules that import nothing. A module sits in wave Ln when its deepest dependency sits in Ln−1. Every module in a wave can be ported at the same time, as soon as the previous waves are done. python scripts/deps.py --layers prints Kestrel's seven waves.

The width of a wave is how many modules it holds. Width is the most agents that wave can keep busy. Kestrel's widest wave is L3 with 14 modules: the twelve ops/* modules plus io/ppm and io/pgm.

The critical path is the longest chain of dependencies. For Kestrel it is mathutil → color → image → (any op) → steps → runner → cli, seven modules long. python scripts/deps.py --critical prints it. However many agents you run, the port cannot finish faster than the time it takes to do those seven modules one after another.

Part threeThe arithmetic of waves

Once you have waves, you can reason about time and agent count without running anything. Use a toy number to see the shape. These numbers are illustrative. Say every module takes one agent 10 minutes, including its verify loop.

Predict first

One agent porting all 24 modules in order takes 240 minutes (illustrative). You now have as many agents as you want, and you wait for each wave to finish before starting the next. How long does the port take? And how long with exactly 4 agents?

The answer

With unlimited agents, each wave takes one module's time, so 7 waves × 10 minutes = 70 minutes. That is a 3.4x speedup, and it is the ceiling: agent number 15 has nothing to do, because no wave is wider than 14.

With 4 agents, every wave except L3 still takes one round. L3 has 14 modules, so it needs four rounds (4 + 4 + 4 + 2). That is 6 + 4 = 10 rounds, or 100 minutes. Going from 4 agents to 14 saves 30 minutes, and all of the saving comes from one wave.

Real modules are not all 10 minutes. A wave lasts as long as its slowest module. If ops/blur.py takes three times as long because of the T1 rounding trap, all of L3 waits for it. This is the cost of a wave barrier: a point where everyone stops until the last worker arrives.

There is a second, less visible cost. Every extra agent adds coordination: a handoff message to write, a report for the orchestrator to read, another set of edits that might collide with someone else's. At 4 agents that tax is small. At 14 it starts to matter, and Lessons 12 and 14 are about keeping it down. Past the width of the widest wave, extra agents add only tax.

Part fourPlan in waves, run from a ready queue

Waves are a simplification. A wave barrier says "start nothing in L4 until every L3 module passes". Look at analysis/edges. It needs ops/grayscale and core/mathutil, nothing else. Once grayscale passes, edges can start, even while blur is still fighting its rounding trap.

A ready queue is the list of modules whose dependencies are all done. python scripts/status.py --next prints it. A scheduler that pulls work from the ready queue never waits for an unrelated slow module. Notice what it cannot do: pipeline/steps imports all twelve ops, so it still waits for the slowest one. The critical path stays seven modules long.

So use both. Plan in waves, because a wave plan is easy to read, review and budget. Execute from the ready queue, because it wastes less time. The plan tells a human what will happen. The ready queue tells the orchestrator what to do next.

Part fiveThe plan is a file

At three agents, the orchestrator can keep the plan in its head, which means in its context window. At fifteen, that plan competes with fifteen reports for space, and Lesson 3 showed what happens to an agent whose context fills up. So write the plan down. PLAN.md becomes the orchestrator's memory, and you can read it too.

A useful PLAN.md for Kestrel has one section per wave and one line per module with five things: its status (done, ready, or blocked and by what), its owner (one porter per module), its gate (scripts/verify.sh kestrel/<path>.py), a turn or budget cap, and any known trap that applies (T2 for resize and rotate, T3 for pad). The plan should also say which modules are on the critical path, so you know where delays hurt.

Two rules keep the plan honest. First, derive it. The waves come from deps.py and the status comes from status.py, so regenerate those parts rather than editing them by hand. Second, the plan describes intent and the repo describes reality. When they disagree, the repo wins. Lesson 12 makes that rule precise.

Where you are. After Weeks 1 and 2 your status.py table shows waves L0 to L3 done (all twelve ops plus both io modules) and analysis/stats done. What remains is analysis/edges, unless you took the Week 2 stretch, and the pipeline chain: steps, runner, cli. This lab writes the plan for the whole graph and finishes the analysis package. Stretch

Key takeaway

Parallel agents need a dependency graph before they need anything else. The width of the widest wave caps how many agents help, and the critical path caps how fast you can go, so write both into the plan and spend your effort on the path.
