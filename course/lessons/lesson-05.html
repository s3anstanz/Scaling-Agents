Lesson 05 Week 1 · One agent ~15 min 1 agent

One module end to end, and when one agent is enough

Put the week together into one repeatable recipe, run it on two modules, and record a baseline. Then decide, with the baseline in hand, when a second agent would actually help.

Part oneThe single-agent recipe

Four lessons, four ingredients. Each one fixed a specific way a single agent goes wrong, and together they make a run you can repeat, measure and trust.

One more rule ties them together: work in dependency order. Each run ports one module whose dependencies are already ported and passing. python scripts/status.py --next lists exactly those. A run that starts on a module with missing dependencies tends to widen its own scope, which is the never-stopping failure from Lesson 02.

Part twoRunning it on image and blur

After Lab 04 you have errors, mathutil, color and geometry. That makes kestrel/core/image.py ready: it imports color, geometry and errors, all ported. image is the hub of the library. All twelve ops/ modules and both io/ modules import it, so its API (the Image class, blank, get, with_pixels, rows) becomes a contract that fourteen later ports depend on. Getting its names right, per MIGRATION.md, matters more here than anywhere else in Week 1.

With image ported, ops/blur.py becomes ready. This is the module from Lesson 04's story, and it carries trap T1: every channel average goes through round_half_even. This time the Known traps entry you wrote in Lab 03 is in the contract, and the gate is in place behind it. You will see whether the agent gets it right first time, and how much cheaper the run is when it does.

The gate lives in your project settings, so it also runs at the end of headless runs. A headless run that tries to finish with a failing module gets sent back once, exactly like an interactive one.

Predict first

Of the modules you will have ported by the end of this lab (errors, mathutil, color, geometry, image, blur), which do you expect to be the most expensive, and why?

The answer

Most likely image. Cost follows two things: how much the agent has to read and write, and how many times it goes around the loop. image has the largest API, the most validation logic and tests, and it imports three ported modules whose TypeScript names it must read and use. errors should be the cheapest. mathutil and blur are small, but a trap that bites adds iterations, and each iteration costs more than the last because the context keeps growing. If blur comes in cheap, that is the Known traps entry paying for itself.

Part threeThe baseline

Part fourWhen one agent is enough

A single agent with this recipe is a strong default. It is the cheapest setup, the easiest to debug, and every decision in it is made with full context. Add agents only when one of four signals appears.

  1. Context overflow. The task needs more than one window can hold well. pipeline/steps.py imports all twelve ops; an agent that needs to understand all of them at once, plus the steps code, plus test output, is a candidate for splitting the reading across helpers that return summaries.
  2. Independent parallel work. Units that do not depend on each other. Wave L3 is fourteen modules with no edges between them. Waves L0 to L2 are a chain; there, nothing can run in parallel.
  3. A need for independent judgement. A check by someone who did not do the work. Lesson 04 showed that the porting agent also ports the tests; a reviewer with a fresh context and no edit tools can catch a weakened test that the author never will.
  4. Wall-clock pressure. The sequential estimate from your baseline is longer than you can wait. If 24 modules at your average time is a working day, that matters; at 240 modules it decides the project.

The opposite signal matters as much. Anthropic's write-up of its multi-agent research system found that a lead agent with parallel subagents beat a single agent by 90.2% on their internal research evaluation. The same post reports that agents use about 4 times the tokens of chat and multi-agent systems about 15 times, and that multi-agent setups fit poorly when agents need shared context or have many dependencies between them, which includes most coding tasks.

That last point is the reason this course spends Week 3 on dependency graphs, contracts and isolation. A migration is coding, so by default it is the kind of task where many agents do badly. It becomes parallel only after you find the structure that lets pieces proceed independently: scripts/deps.py for the order, MIGRATION.md for the shared rules, verify.sh for a check each piece can pass alone. When work is tightly coupled, one agent with the whole picture is usually both cheaper and better.

Make the call

Next on your list is analysis/stats.py.

The situation
  1. Its only dependency, ops/histogram, is ported and passing.
  2. It is one small module with its own tests.
  3. No deadline; you would like it done today.

Decide, then see the reasoning.

Right call

None of the four signals is present. It fits in one context, there is nothing to parallelize, the tests are the independent judge, and there is no time pressure. A team would cost several times more for the same result.

Not quite

There is nothing to split. A planner, a porter and a reviewer for one small module triple the tokens and add handoffs, and the tests already provide the independent check.

Make the call

Your manager wants all of wave L3 ported by tomorrow morning.

The situation
  1. image, color, geometry, mathutil and errors are ported and passing.
  2. The 14 L3 modules depend only on those, not on each other.
  3. Your baseline says one module at a time would take most of a working day.

Decide, then see the reasoning.

Not quite

One agent will get there, but it misses the deadline you were given, and a single session porting fourteen modules suffers context rot. At minimum you would run fourteen separate sessions, one after another.

Right call

Two signals at once: independent parallel work and wall-clock pressure. The contract and per-module check already exist. Expect to pay more in tokens and to deal with one shared file, the barrel ts/src/index.ts, which Week 3 covers.

Make the call

Halfway through the ops, you decide the TypeScript Image should store pixels as a flat typed array instead of an array of tuples.

The situation
  1. The change is to ts/src/core/image.ts, whose API every ported op uses.
  2. Seven ops are already ported and read pixels directly.
  3. Every op's tests must still pass afterwards.

Decide, then see the reasoning.

Right call

This is tightly coupled work: one shared contract and every consumer of it, changing together. It is exactly the case where multi-agent setups fit poorly. One agent holding the new Image design and applying it consistently across seven files will do better than seven agents each guessing at it.

Not quite

Seven files looks parallel, but every edit depends on one design decision in image.ts. Split it and each agent needs the full shared context anyway, and they will drift apart in small ways the tests may not catch.

Lab 05 · In Claude Code ~20 min · est. $0.50–$2.50

Goal. Port core/image and ops/blur with the full recipe, then turn your run records into notes/baseline.md.

  1. From the repo root, activate the environment, confirm the tree is clean, and check what is ready. --next should list core/image.

    source .venv/bin/activate
git status --short
python scripts/status.py --next

  2. Port image with the full recipe. The Stop hook from Lab 04 is active for this run.

    start=$SECONDS
claude -p "Port kestrel/core/image.py to TypeScript at ts/src/core/image.ts and its tests from tests/core/test_image.py to ts/test/core/image.test.ts. Follow MIGRATION.md, including its Known traps, and import from the modules already ported in ts/src/core/ instead of reimplementing them. Add the module's export line to ts/src/index.ts and do not edit any other module's files. Run scripts/verify.sh kestrel/core/image.py and keep fixing until it exits 0. If the same test fails the same way twice in a row, stop and report the failure instead. Finish with three lines: what you ported, how many verify runs it took, and any trap you met." \
  --model sonnet \
  --max-turns 20 --max-budget-usd 1 \
  --output-format json \
  --permission-mode acceptEdits \
  --allowedTools "Read,Edit,Write,Glob,Grep,Bash(scripts/*),Bash(./scripts/*),Bash(python scripts/*),Bash(python -m pytest*),Bash(npx vitest*)" \
  > notes/runs/image.json
echo "image $((SECONDS - start))" >> notes/runs/seconds.txt
python scripts/runinfo.py notes/runs/image.json
scripts/verify.sh kestrel/core/image.py; echo "exit=$?"

  4. Create a script that turns the run records into the baseline table. It skips the bare-mode experiment from Lab 03, and marks the interactive geometry session, which has no JSON record.

    import json
from pathlib import Path

RUNS = Path("notes/runs")

rows = [
    "| module | turns | cost (USD) | minutes | ended as |",
    "|---|---|---|---|---|",
]
for line in (RUNS / "seconds.txt").read_text().splitlines():
    name, seconds = line.split()
    if name.endswith("-bare"):
        continue
    record = RUNS / f"{name}.json"
    run = json.loads(record.read_text()) if record.exists() else {}
    cost = run.get("total_cost_usd")
    cost_cell = f"{cost:.2f}" if cost is not None else "from /usage"
    rows.append(
        f"| {name} | {run.get('num_turns', 'n/a')} | {cost_cell} "
        f"| {int(seconds) / 60:.1f} | {'error' if run.get('is_error') else run.get('subtype', 'interactive')} |"
    )

table = "\n".join(rows)
Path("notes/baseline.md").write_text(
    "# Week 1 baseline: one agent per module, sonnet\n\n" + table + "\n"
)
print(table)

Stretch

Add a line under the table in notes/baseline.md with your average minutes per module, times 24 (the starter) and times 240 (the full story library), labelled as estimates. Then list the modules status.py --next shows now. That list is the work a team could start on in parallel.

Key takeaway

Context file, bounded loop, verification gate, cost cap: with these, one agent is reliable, and your baseline says what it costs. Add agents only for overflowing context, independent parallel work, independent judgement or wall-clock pressure, and not for tightly coupled work.
