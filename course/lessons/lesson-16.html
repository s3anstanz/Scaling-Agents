Workflows: orchestration as code

Until now a model decided who to spawn, in what order, and when to stop. A workflow moves those decisions into a short JavaScript file. The shape of the work becomes code you can read, rerun and save, while each step inside it is still a full agent.

Part oneWho decides the next step?

Every multi-agent run you have done so far had a lead. In Lesson 11 the lead read PLAN.md and chose which subagents to start. In Lesson 13 the lead of an agent team created tasks and waited for teammates. In both cases the orchestration lived inside a model's head. Call this model-driven orchestration. The lead looks at the situation and picks the next step, the same way a single agent picks its next tool call.

Model-driven orchestration is flexible. If ops/blur.py turns out to need a helper nobody planned for, the lead can notice and adapt. That flexibility has a price, and the price grows with the number of agents.

  • It varies. Ask a lead to port 14 modules and it might start 14 subagents. Ask again and it might group them into four batches, or port two itself because they looked easy.
  • It forgets. Every subagent report lands in the lead's context. By report twelve, report three is far back, and a module can quietly drop out of the plan.
  • It is hard to resume. If the session dies halfway, the plan was in a context window that no longer exists.
  • It costs judgment where none is needed. "For each ready module, port it, then verify it" is a loop. Asking an expensive model to rediscover that loop on every run is waste.

The alternative is scripted orchestration. You write the graph down as code: the loops, the fan-out, the conditions. Each node in that graph is still a real agent with its own tools and its own loop. The script decides which agents run and in what shape. The agents decide how to do their piece.

Anthropic's "Building effective agents" post draws the same line. It calls systems where code defines the path workflows, and systems where the model directs its own process agents. Its advice is to start with the simplest thing that works. Claude Code's workflow feature lets you mix the two: code owns the graph, agents own the nodes.

Predict first

You ask a model-driven lead to port the 14 modules of wave L3 with subagents, and you run the exact same prompt twice on a fresh copy. Then you do the same with a workflow script. What changes between the two runs in each case?

The answer

With the lead, almost anything can change: how many subagents start, which modules share a subagent, whether each one is verified separately, and whether the lead ports a couple of "easy" ones itself. With the script, the graph is identical both times: one finder, 14 port agents, 14 verify agents, one report. What still varies is inside each agent (how blur.ts handles banker's rounding, how many turns it takes). That is the variation you want to keep, because it is where the real work happens.

Part twoThe script API in one page

A workflow is a plain JavaScript file. It is not TypeScript, and it is not a Node program with access to your disk. It is a coordinator. It calls a small set of functions the runtime provides, and agents do everything that touches the repo.

CallWhat it doesKestrel use
agent(prompt, opts)Starts one agent and waits for its final answer. Returns text, an object when opts.schema is set, or null if it failed. Options include label, phase, schema, model, effort, isolation: 'worktree' and agentType (reuse a .claude/agents/ definition).Port kestrel/ops/pad.py on haiku, return { module, status, traps }.
parallel([() => ..., ...])Runs every thunk at once and waits for all of them. A barrier. It never rejects: a thunk that fails becomes null in the result array.Three strategy agents that must all finish before a planner compares them.
pipeline(items, s1, s2, ...)Each item flows through the stages on its own. No barrier between stages.Port then verify, per module, so fast modules do not wait for slow ones.
phase(title), log(msg)Label progress in /workflows and print lines to the run log.phase('Port and verify'), log('11/14 green').
args, budgetThe input you passed when starting the run, and the run's budget: budget.total and budget.remaining().A --small flag; stop before a wave when little budget is left.
workflow(name, args)Runs another workflow as one step. Nesting goes one level deep.A top-level migrate that calls port-wave.

The whole surface area. Everything else is ordinary JavaScript: variables, loops, if, map, filter.

Three rules keep a script valid. First, it begins with export const meta = {...}, and that object must be a pure literal: a name, a description, and a list of phases whose titles match your phase() calls. Second, the script never calls Date.now() or Math.random(), never reads files and never runs shell commands. If you need the list of ready modules, an agent runs python scripts/status.py --next and returns it. Third, because parallel() turns failures into null, you almost always follow it with .filter(Boolean) before reading results.

The schema option deserves a moment. In Lesson 12 you passed --json-schema to headless runs so every worker returned the same fields. Inside a workflow the same idea is one option. Give agent() a JSON Schema with type: 'object', properties and required, and you get back an object your script can branch on. No regex over prose, no "the agent said it mostly worked".

The difference between parallel and pipeline matters more than it first looks. Wave L3 mixes quick modules like invert with slow ones like blur, which hits the T1 rounding trap and usually needs a few extra turns. With two parallel calls (port all, then verify all), every verify waits for the slowest port. With pipeline(modules, port, verify), invert is verified and done while blur is still on its third attempt.

Annotations

Click a marked line to see why it is there.

Line 1 · meta

The header the runtime reads before anything runs. It must be a plain literal: no variables, no function calls. The name becomes the slash command when you save the file to .claude/workflows/, so this one runs as /port-wave.

Line 4 · phases

The phase titles shown in /workflows. Each one matches a phase() call below, character for character. Port and verify share one phase on purpose, because pipeline() interleaves them.

Line 7 · schema

A JSON Schema for the answer. With schema set, agent() returns an object instead of prose, so the script can loop over modules without parsing text. This is the Lesson 12 contract, moved inside the script.

Line 17 · closed vocabulary

An enum stops a worker from inventing statuses like mostly done. The script only has to handle two values.

Line 30 · a scout agent

The script cannot run shell commands itself, so a cheap agent runs scripts/status.py --next and hands back the list. Anything that touches the repo goes through an agent.

Line 33 · null-safe

agent() returns null when the agent fails. Treat that as an empty wave instead of crashing the run.

Line 37 · stage one

Each pipeline stage is a function from one item to the next value. Returning { module, port } carries the module name forward, so stage two knows what to verify even if the port agent returned nothing.

Line 42 · the exit condition

The same rule as Lesson 4, written into every worker prompt. The command decides done, and the worker is told exactly which command it is.

Line 43 · per-call model

A model on the call outranks every other model setting, including CLAUDE_CODE_SUBAGENT_MODEL. Bulk porting goes to the cheap model; the verify step catches what it gets wrong.

Line 45 · independent check

A second agent that only runs scripts/verify.sh and edits nothing. The porter's own claim never decides the result. A fresh agent with no stake in the port does.

Line 51 · pipeline, no barrier

Each module flows through port then verify on its own. A quick module like invert is verified while blur is still porting. filter(Boolean) drops any item whose stages failed outright.

Line 59 · traps go to a human

The script collects traps and prints them. It does not write MIGRATION.md from 14 agents at once, which would break the single-writer rule from Lesson 12.

Notice what the script does not contain. It has no instructions on how to port a module. Those live in MIGRATION.md and CLAUDE.md, which every agent loads. The script holds only the shape: find, fan out, port, check, report. That separation is what lets you reuse it for every wave.

Count the agents. For the L3 wave that is 1 finder, 14 porters and 14 verifiers, so 29 agents. Remember that number for Part four.

Part fourSaving, running, watching, and the limits

You rarely type a workflow from scratch. You ask for one in plain words ("use a workflow to port every ready module"), or you include the keyword ultracode in a prompt. Claude writes the script and runs it. If you want Claude to plan a workflow for every substantive task in a session, /effort ultracode does that. On a Pro plan, turn on "Dynamic workflows" in /config first.

While a workflow runs, /workflows shows live progress: phases, agents, their labels and status. Three keys matter. p pauses, x stops, and s saves the script. A saved workflow lands in .claude/workflows/ for the project (or ~/.claude/workflows/ for you everywhere), and from then on it runs as a slash command named after its meta.name. Ours becomes /port-wave.

Workflows have limits, and at this scale you will meet them.

LimitDefaultWhat it means for Kestrel
Agents running at onceUp to 16 (CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS, 1 to 256). Smaller machines can start with fewer, so this week's launch commands set it to 16.The 14-module wave fits. A 140-module wave in the full library would run in batches.
Agents per run1,000Plenty for 24 modules. At 240 modules with verify and retry agents, you start to plan around it.
Items per parallel or pipeline call4,096Not a concern for Kestrel.
"Large workflow" warningAbove 25 agents (50 with workflowSizeGuideline: "large") or about 1.5M projected tokensWith this week's large setting, Kestrel's runs stay under it. It is a prompt to check the plan, not an error.
workflowSizeGuidelinemedium (under 10 agents)Claude sizes the workflows it writes to this guideline. Options are small (under 5), medium, large (under 50) and unrestricted. For this week, use large.

The size guideline shapes what Claude proposes. The concurrency cap shapes how fast it runs. Leave the cap at 16 until Lesson 19.

Make the call

Your team keeps Kestrel's port moving every evening while the Python library keeps changing. Should the evening run be a prompt to a lead, or a saved workflow?

The situation
  1. Every evening, port whatever scripts/status.py --next lists.
  2. Every module must pass scripts/verify.sh before it counts.
  3. New traps go into a report for a human, never straight into MIGRATION.md.
  4. When it fails, you want to compare tonight's run with last night's.

Decide, then see the reasoning.

Not quite

A lead could do it, but every evening it would rebuild the graph from scratch and might build a different one. Comparing two runs is hard when their shapes differ. Nothing here needs fresh judgment about structure.

Right call

You can write the graph down before it starts: find, port, verify, report. That is the test for a workflow. Saved as /port-wave, it runs the same shape every night, so a difference in results points at the code or the library, not at the orchestration.

The same ideas in code. The Agent SDK (claude-agent-sdk in Python, @anthropic-ai/claude-agent-sdk in TypeScript) lets you build this kind of orchestration in your own program. The labs stay in the CLI, where workflows give you the progress view and saving for free.

    export const meta = {
  name: 'port-wave',
  description: 'Port every module in the next ready wave, one agent per module, each checked by scripts/verify.sh',
  phases: [{ title: 'Find' }, { title: 'Port and verify' }, { title: 'Report' }]
}

const listSchema = {
  type: 'object',
  properties: { modules: { type: 'array', items: { type: 'string' } } },
  required: ['modules']
}

const portSchema = {
  type: 'object',
  properties: {
    module: { type: 'string' },
    status: { type: 'string', enum: ['ported', 'stuck'] },
    traps: { type: 'array', items: { type: 'string' } }
  },
  required: ['module', 'status', 'traps']
}

const verifySchema = {
  type: 'object',
  properties: { passed: { type: 'boolean' }, error: { type: 'string' } },
  required: ['passed']
}

phase('Find')
const ready = await agent(
  'Run python scripts/status.py --next. Return the module ids it prints, one per line, like core/color. Edit nothing.',
  { label: 'find ready wave', model: 'haiku', schema: listSchema })
const modules = ready?.modules ?? []
log(`Ready wave: ${modules.length} modules`)

phase('Port and verify')
const port = async (m) => ({
  module: m,
  port: await agent(
    `Port ${m} and its tests to TypeScript, following MIGRATION.md.
Port every Python test as it("test_name"). Edit only this module's files under ts/src and ts/test. Never edit ts/src/index.ts.
You are done only when scripts/verify.sh ${m} exits 0. Report any Python-vs-JS trap you hit.`,
    { label: `port ${m}`, model: 'haiku', schema: portSchema })
})
const verify = async (p) => ({
  ...p,
  check: await agent(
    `Run scripts/verify.sh ${p.module}. Edit nothing. passed is true only if it exits 0; error is the first failing line.`,
    { label: `verify ${p.module}`, model: 'haiku', schema: verifySchema })
})
const results = (await pipeline(modules, port, verify)).filter(Boolean)

phase('Report')
const green = results.filter((r) => r.check?.passed)
log(`${green.length}/${modules.length} green`)
for (const r of results) {
  if (!r.check?.passed) log(`RED ${r.module}: ${r.check?.error ?? 'verify agent failed'}`)
}

if (traps.length) log(`Traps to add to MIGRATION.md: ${traps.join('; ')}`)

What you should see

Four runs with the same shape: one finder, then a port and a verify per module. The fourth run starts 14 porters at once, all within the cap of 16 you set at launch. A few ops usually come back red on the first pass. blur trips T1 rounding, pad trips T3 modulo, and resize or rotate may trip T2 floor division if mathutil's port hid it. The report lists those traps for you to add to MIGRATION.md. Exact counts and cost vary by run.

Stretch

Edit the saved script so a red module gets one retry on sonnet, with the verify error pasted into its prompt, before it is reported red. Rerun on a fresh reset and compare the green count and /usage.

Key takeaway

When you can draw the graph before the work starts, write it as a workflow. Code owns the shape, agents own the work inside each node, and the run looks the same every time you start it.
