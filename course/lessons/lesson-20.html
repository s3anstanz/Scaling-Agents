Lesson 20 Week 4 · Scale ~20 min 100 agents

Capstone: design the 100-agent migration

Nineteen lessons gave you the parts: loops, verification, roles, graph shapes, contracts, isolation, workflows, trees, breakers and a cost model. This lesson assembles them into one design for porting all of Kestrel, then has you build and run a scaled-down version of it end to end.

Part oneThe problem, stated once

Port the full Kestrel library, about 240 Python modules, to TypeScript. The dependency graph has 7 waves, and the middle wave is very wide (about 140 modules in the story). The critical path is 7 modules long. The traps are real: banker's rounding, floor division, negative modulo, default sort order, and PPM header parsing, plus whatever the full library adds that nobody has found yet.

Three requirements shape every decision. Correct means every module passes scripts/verify.sh and the TypeScript pipeline produces the same bytes as Python on every sample, as checked by scripts/difftest.py. Affordable means spend is bounded, and a broken dependency cannot burn a whole wave's budget. Steerable means a human can see what is happening, stop it, and approve the moments that matter, without reading 240 reports.

Recall what Anthropic's research post said: multi-agent systems fit poorly when agents need shared context or have many dependencies, which includes most coding tasks. Everything below is a way of removing those two obstacles before adding agents. The dependency graph removes the hidden dependencies. Contracts and shared files replace shared context. Isolation keeps parallel writers apart. Only then does the fleet make sense.

Part twoThe design, layer by layer

  1. Explore before committing: a double diamond on top. The approach is genuinely uncertain. Should you port strictly wave by wave, attack the trap-heavy modules first, or port every test before any code? A wrong choice gets multiplied 240 times. So the first diamond diverges into three strategy agents and converges on one planner, which writes PLAN.md. Exploring costs a few agents; porting 240 modules the wrong way costs a few hundred.
  2. Human checkpoint one: approve the plan. You read PLAN.md and mark it approved. Nothing ports at scale until you do.
  3. Build along the DAG. The second diamond's fan-out follows scripts/deps.py --layers. Each wave is a barrier; within a wave, a pipeline moves each module through port, verify and fix on its own.
  4. A tree of leads. Sub-leads per package (and group leads under ops/, which is too wide for one) re-check red modules and send up five lines each. The top lead and you read only those.
  5. Isolation and ownership. Each porter owns its module's files and nothing else. At 240 modules and 100 agents, porters also get their own worktrees (isolation: 'worktree') so a stray edit cannot reach a neighbour. One integrator is the only writer of ts/src/index.ts and the Known traps section of MIGRATION.md.
  6. Loops at three levels. A verify loop per module with a retry cap and an escalation to a stronger model. A canary and circuit breaker per wave. A budget guard before every wave, so the run stops at a clean boundary.
  7. An end-to-end gate. Unit tests can all pass while modules disagree about a contract. The difftest compares real output bytes from both implementations and bisects any mismatch to a module.
  8. Human checkpoints two and three. A small first run (one wave) before the full run, and your sign-off after the difftest.
Predict first

Look at the figure and pick the one component whose removal would hurt most at 100 agents. The tree? The breaker? The double diamond? Something else?

The answer

The small verify boxes. Every other part of the design assumes that "green" means something: the breaker counts red, the sub-leads count green, idempotent reruns skip green, the integrator exports green, and the cost model divides by green. Remove the mechanical check and all of them start optimising for "the agent said it was done", which is the Lesson 4 failure multiplied by a hundred. A close second is the dependency graph, because without it parallel agents guess at APIs that do not exist yet.

Part threeHow many agents, and which shape?

The capstone uses every tool, but most problems should not. The scale of a system should follow from the work, and the shapes from Lesson 9 tell you what the work looks like. Here is the whole course as one decision guide.

Move down a row only when the row above stops working. Each step down adds cost and coordination that must buy something you can name.

Notice the "proven recipe" condition in the last row. A 100-agent run multiplies whatever your recipe does, good or bad. That is why the Week 4 labs started small: one wave, then a canary, then the whole starter. You would never launch 100 agents on a recipe you had not watched work on 24.

Make the call

For the 24-module starter run in today's lab, should each porter get its own worktree?

The situation
  1. Every porter owns a distinct pair of files: its module and its test.
  2. Porters never touch ts/src/index.ts or MIGRATION.md; one integrator writes both.
  3. At most 14 porters run at once.
  4. Worktrees would need a merge step after every wave.

Decide, then see the reasoning.

Not quite

Safe, but you pay for a merge stage that solves no problem you have. With disjoint files and a single writer for shared ones, there is nothing for 14 porters to collide on.

Right call

Ownership rules already make collisions impossible at this size. At 240 modules and 100 agents the odds of one stray edit rise, and so does the cost of finding it, which is when the design adds worktrees and a merge step.

Part fourThe design as one workflow

Here is the design written as a single workflow, sized for the starter. It runs in two modes. --small explores, plans and ports only the first wave, so you can check the recipe. --plan-approved skips exploration, ports every remaining wave and finishes with the difftest. At 24 modules the script plays the lead and the sub-leads only summarise; at 240 each sub-lead would own its package's pipeline, as in Lesson 17. Click the marked lines.

Annotations

Click a marked line to see why it is there.

Line 7 · two run modes

--small runs one wave as a dry run. --plan-approved skips exploration and uses the plan you signed off. The script accepts the arguments as a string or an object.

Line 12 · budget guard

Checked before every wave. When less than 15% of the budget is left, the run stops at a wave boundary, where everything is either green or clearly not.

Line 15 · ownership rules

One string reused in every worker prompt: own your module's files, never the barrel, never MIGRATION.md, report blocked dependencies. This is Lesson 14's isolation, written as policy.

Line 31 · diamond one, diverge

Three agents propose different strategies in parallel. Exploration is cheap compared with porting 240 modules the wrong way.

Line 39 · diamond one, converge

One planner on the strongest model chooses or merges the strategies and writes PLAN.md. This is the one place in the run where judgment matters most, so it gets opus.

Line 41 · human checkpoint

The script cannot ask you a question, so the checkpoint is a run boundary. You read PLAN.md, add APPROVED, and start the next run. Without that line, the planner returns no waves.

Line 47 · idempotent porter

Checks status first and skips green modules. That is what makes a halted run safe to restart.

Line 52 · independent verify

A separate agent runs scripts/verify.sh and edits nothing. Its exit code, not the porter's claim, sets the status.

Line 59 · the verify loop

Up to two fix rounds on sonnet, each fed the last error, each re-verified. Escalating the model only on failure keeps the bulk work cheap.

Line 76 · canary for wide waves

Waves wider than six send three modules first. The starter's L3 wave of 14 gets a canary; the small waves just run.

Line 77 · diamond two, diverge

Port, verify and fix flow per module with no barrier. The wave boundary is the only barrier, because the next wave depends on this one.

Line 82 · circuit breaker

If more than 30% of a wave is red (an illustrative threshold), stop before the next wave builds on broken modules.

Line 88 · sub-leads

One sub-lead per package re-checks red modules and writes five lines. At 24 modules the script itself plays lead; at 240 each sub-lead would own its package's pipeline, as in Lesson 17.

Line 94 · single writer

One integrator regenerates the barrel with scripts/gen_barrel.py and appends traps. No porter ever touches those files, so parallel porters cannot conflict on them.

Line 102 · the end-to-end gate

Every module can pass its own tests while the pipeline still produces different bytes. The difftest compares real output from Python and TypeScript, and bisects when they differ.

Line 109 · hand back to a human

Every run ends with an instruction for you: fix and rerun, approve the plan, or sign off.

  type: 'object',
  properties: { module: { type: 'string' }, status: { type: 'string', enum: ['passed', 'failed', 'skipped', 'blocked'] }, traps: list, error: { type: 'string' } },
  required: ['module', 'status', 'traps']
}
const verifySchema = { type: 'object', properties: { passed: { type: 'boolean' }, error: { type: 'string' } }, required: ['passed'] }
const e2eSchema = { type: 'object', properties: { specs: list, failing: list, suspect: { type: 'string' } }, required: ['specs', 'failing'] }

let strategies = []

  phase('Explore')

  `Port ${m} and its tests to TypeScript. First run python scripts/status.py --json; if ${m} is already passing, return "skipped". ${RULES}
You are done only when scripts/verify.sh ${m} exits 0. List any new Python-vs-JS trap you hit.`,
  { label: `port ${m}`, model: 'haiku', schema: resultSchema })) ?? { module: m, status: 'failed', traps: [], error: 'agent returned nothing' }

const verify = async (r) => {
  if (r.status === 'skipped' || r.status === 'blocked') return r
  const v = await agent(`Run scripts/verify.sh ${r.module}. Edit nothing. passed is true only if it exits 0; error is the first failing line.`,
    { label: `verify ${r.module}`, model: 'haiku', schema: verifySchema })
  return { ...r, status: v?.passed ? 'passed' : 'failed', error: v?.error ?? r.error }
}

const fixLoop = async (r) => {
  for (let i = 1; i <= MAX_FIXES && r.status === 'failed'; i++) {
    const f = await agent(
      `scripts/verify.sh ${r.module} fails with: ${r.error ?? 'unknown'}. Read the failure, then fix ${r.module}. ${RULES} You are done only when scripts/verify.sh ${r.module} exits 0.`,
      { label: `fix ${r.module} #${i}`, model: 'sonnet', schema: resultSchema })
    r = await verify({ ...r, ...(f ?? {}), module: r.module })
  }
  return r

const waves = small ? plan.waves.slice(0, 1) : plan.waves

}

What you should see

The small run ends with two green modules, a PLAN.md and a message telling you to approve it. The full run ports the remaining 22 modules in six waves, sends a canary ahead of the 14-module wave, shows a handful of fix rounds on sonnet, and ends with sub-lead summaries, a regenerated barrel, appended traps and a difftest result. Most runs finish with all or nearly all modules green; a red module usually comes with a precise cause from its sub-lead. Your retrospective should compare a prediction you made with something you measured.

Stretch

Make the script ready for 240. Add isolation: 'worktree' to the port and fix agents, add an integration step that merges each wave's worktree branches before the next wave starts, and move each package's pipeline under its sub-lead, as in Lesson 17. Rerun on a fresh reset and add the cost of the extra machinery to RETRO.md.

Key takeaway

A hundred agents is a design, not a setting. Remove the hidden dependencies, make "done" mechanical, bound every loop, compress reports on the way up, and put humans at the few boundaries where their judgment is cheap and decisive. Then scale only as far as the cost curve keeps paying.
