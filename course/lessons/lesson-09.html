Lesson 09 Week 2 · Small teams ~17 min 3–5 agents

Graph shapes: chain, diamond, double diamond

Every team of agents has a shape, whether you drew it or not. This lesson gives you five shapes, a two-question test for when the double diamond earns its cost, and a lab where you run one on the rest of ops/.

Part oneWhat graph engineering means

Draw any multi-agent run as a graph. The nodes are agents or steps: the lead, a planner call, a porter call, a run of verify.sh. The edges are handoffs: a brief going out, a report coming back. Graph engineering is choosing that shape on purpose and wiring it.

The shape decides four things. What runs in parallel. Where results meet and have to be merged. Where detail gets lost, since every edge is a lossy handoff that carries only a report. And where the checks sit. Change the shape and you change the speed, the cost and the failure modes of the whole run, even with the same agents and the same prompts.

None of this is new. Anthropic's "Building effective agents" names the same patterns: prompt chaining, parallelization (sectioning and voting), orchestrator-workers, and evaluator-optimizer. Its first piece of advice also applies here: start with the simplest shape that works and add structure only when it pays for itself.

Part twoChain: when each step needs the last one's output

A chain is a sequence. Step two starts when step one finishes and uses what it produced. Anthropic calls this prompt chaining. You built one in Lab 08 for a single module: planner, then porter, then reviewer. The core wave was also a chain: mathutil, then color, then image, because each import has to exist before the next module can pass its tests.

Use a chain when the dependency forces the order. It is the easiest shape to debug, because there is one path and you can read it top to bottom. Its costs are speed, since nothing overlaps, and error propagation. A mistake early in the chain flows into every later step, and every hop is a handoff that drops detail. Keep chains short and put a check at the end.

Part threeDiamond: one split, many workers, one merge

A diamond fans out and then fans back in. One node splits the work, several workers run in parallel, and one node merges the results. Anthropic's names for it are parallelization by sectioning and orchestrator-workers. Lab 06 was a diamond with the lead as both splitter and merger.

A diamond works when three things are true. The approach is known, so the splitter can write each worker's brief without guessing. The pieces are independent, so no worker needs another's output. And the merge is cheap, so combining results does not cost more than the parallelism saved. The four remaining ops (rotate, resize, contrast, histogram) pass the first two tests easily. You have ported seven ops the same way, and none of the four imports another.

Step through it · the diamond
  1. The splitter reads python scripts/status.py --next and MIGRATION.md. The approach is settled: one porter call per module, same rules as the last seven ops. Its only real decision is how to group the work.
  2. Fan-out. Each package gets a short brief: the module paths, plus the trap that applies. rotate and resize share trap T2, so they go to one package and the lead can pass the first one's T2 notes to the second.
  3. The workers run in parallel, each in a fresh context. Wall-clock time is now the slowest package, which is the two-module one. A diamond is only as fast as its heaviest branch, so balance matters.
  4. Fan-in. Three reports arrive. This is the only place results meet, so it is where collisions show up: three edits to ts/src/index.ts, or two packages that each wrote a private floorDiv.
  5. The merger runs scripts/verify.sh on all four modules and python scripts/status.py. One check covers the whole fan-in. If the split was clean, this step is short. If it was not, the merge cost eats the time the parallelism saved.
Predict first

All three packages in the diamond report VERIFY: pass. Each module's tests pass on their own. What can still be wrong when the reviewer looks at the four modules together?

The answer

Plenty. Two porters may have solved T2 differently: one imports floorDiv from the ported mathutil, the other wrote a private copy. Both pass, and now the codebase has two answers to one question. The barrel can end up with a missing or duplicated export line. Naming can drift between packages if MIGRATION.md left room for choice. Per-module tests cannot see any of this, because each one only looks at its own module. That is why the merge node is a reviewer with rubric items R4 (contract) and R5 (barrel), and why Lesson 15 adds an end-to-end test.

Part fourDouble diamond: decide what to build, then build it

The double diamond comes from design thinking. The UK Design Council popularised it as two diamonds side by side. The first is about finding the right problem: discover (diverge, look widely) and define (converge on one framing). The second is about building the right solution: develop (diverge, try options) and deliver (converge on the finished thing).

For agents it reads like this. The first diamond fans out several explorers, each proposing a different approach, and converges on one plan. The second diamond fans out workers to execute that plan and converges to integrate and verify. The first diamond is Anthropic's parallelization-by-voting pattern applied to plans; the second is an ordinary diamond.

The explorers in the first diamond are cheap if you design them that way. Make them read-only planners and cap each proposal at about fifteen lines. They read the code and return a short proposal. They do not port anything. The expensive part, the build, happens once, after the decision.

Step through it · the double diamond
  1. The lead faces a question it cannot answer by reading one file: what is the best way to port the rest of ops/? Several approaches are plausible, and whichever it picks will be copied into every porter.
  2. Discover. Three planner calls run in parallel, each with one lens: by file, by trap, test-first. They are read-only and capped at fifteen lines, so this costs three small contexts and no edits.
  3. Define. Three proposals come back. The lead compares them against fixed criteria: packages independent, traps named per package, verification by scripts/verify.sh. It picks one or merges the best parts.
  4. The convergence point. The lead writes the chosen plan to notes/ops-plan.md and stops for your OK. This is the cheapest moment in the whole run to change direction, because nothing has been built.
  5. Develop. Now the expensive part: porter calls for each package, packages in parallel. Each brief comes from the plan, so all three share one approach.
  6. Deliver. The reviewer checks all four modules against R1 to R5 and runs python scripts/status.py. One verdict covers the whole build.
  7. Count the cost. Compared with a plain diamond, you paid for three planner calls and one pause. You bought a plan that was argued for before anything was built. Whether that was worth it is the subject of Part five.

Part fiveWhen to use a double diamond

Ask two questions, in this order.

Question 1: Could you write the plan right now? If you know the approach and could brief the workers today, the first diamond has nothing to discover. If people disagree, if the module is a new kind, or if this is your first time at a scale, the approach is uncertain.

Question 2: Once there is a plan, does the build split into independent pieces? If yes, the second diamond pays off through parallel work. If each piece needs the previous one's output, the build is a chain, whatever you decided in the first diamond.

Build splits into independent piecesBuild is sequential
Approach knownDiamond. The remaining four ops today.Chain, or one agent. The core wave in Week 1.
Approach uncertainDouble diamond. Choosing how to port 40 ops in Kestrel-240.Explore, then chain. One exploring diamond, then a sequential build: steps, runner, cli.

The double diamond needs a yes to both questions: uncertain approach, parallel build.

The line to remember. The first diamond buys certainty. The second diamond buys speed. Pay for each one only when you need what it buys.

A useful way to price the first diamond: compare the cost of the explorers with the cost of a wrong approach multiplied by the number of workers that would follow it. For four ops, a wrong approach costs at most four redone ports, and you have seven earlier ops showing that the approach works. The explorers are close to wasted. For Kestrel-240, a wrong approach is copied into a couple of hundred workers before anyone notices. Three read-only explorers are cheap insurance against that. This is why the capstone in Lesson 20 puts a double diamond at the top of the 100-agent design.

Signs that the first diamond is overkill: MIGRATION.md already names the traps, your role files have worked several times on modules like these, or you can predict what the explorers will say. Signs that you need it: your team argues about the approach, the module is unlike anything ported so far, or the build is big enough that a wrong start is expensive to undo.

Part sixTree and cycle

A tree (or hierarchy) is orchestrators of orchestrators. The top lead talks to a few sub-leads, and each sub-lead runs its own workers. You need one when a single coordinator cannot hold all the reports. A useful span of control is about five to ten direct reports. At 240 modules, one lead reading 240 reports is hopeless, so Lesson 17 gives each package (core, ops, io and so on) its own sub-lead that sends up a five-line summary.

A cycle is an edge that loops back: review, then fix, then review again. Anthropic calls it evaluator-optimizer. Use it when quality needs iteration against a bar you can check, such as the reviewer's rubric. A cycle must have an exit: a pass condition and a maximum number of rounds. Lesson 10 builds one.

Shapes combine. Every node in a diamond can contain a cycle. A tree's leaves are usually diamonds. The general form, where any node can depend on any earlier one, is a DAG (directed acyclic graph), and Lesson 11 draws Kestrel's.

Kestrel-240 has another batch of simple pixel ops to port.

The situation
  1. Six ops, each depending only on core/, which is ported.
  2. They look like the ops you have already ported: per-pixel loops, some rounding.
  3. MIGRATION.md lists T1 and T2, and porter.md has worked on every op so far.
  4. A colleague suggests "three strategists first, to be safe".

Decide, then see the reasoning.

Not quite

Nothing here is sequential. The six ops are independent, so a chain leaves easy parallelism unused.

Right call

Question 1 gets a clear yes: you could write the briefs now. Question 2 is also yes. Known approach plus independent pieces is a diamond. Run the lead's split, porters in parallel, and the reviewer as merger.

Overkill

The strategists would rediscover what MIGRATION.md and seven successful ports already tell you. You would pay for three explorers and a pause to buy certainty you already have.

Make the call · 2

Planning the 40 filter ops in Kestrel-240.

The situation
  1. The team disagrees. One camp wants porters to hand-port each op. The other wants one agent to write a script that translates Python to TypeScript mechanically, with porters cleaning up the output.
  2. Nobody has tried the script approach on Kestrel yet.
  3. Whichever approach wins, the 40 ops are independent and depend only on ported modules.

Decide, then see the reasoning.

Not quite

A diamond needs a known approach so the splitter can brief workers. Here the approach is the open question, and a wrong pick would be copied into 40 workers.

Right call

Both questions point here. The approach is uncertain, so explore: have read-only planners each make the case for one approach, maybe with a small trial on two ops, then converge on a plan. The build splits 40 ways, so fan out again and converge on review.

Not yet

Forty reports may eventually need sub-leads, and the build half could become a tree. That is a question about span of control. The first problem is choosing the approach, which a tree does not address.

Make the call · 3

Next up in the starter: pipeline/steps, pipeline/runner and cli.

The situation
  1. runner imports steps, and cli imports runner.
  2. You are unsure how to port the step registry in steps.py: a map from names to functions, or a switch.
  3. The choice affects how runner calls steps.

Decide, then see the reasoning.

Half right

The first diamond fits, because the approach is uncertain. The second does not: the three modules depend on each other, so there is nothing to fan out. Three parallel porters would wait on each other.

Right call

Uncertain approach, sequential build. Let two or three planners argue the registry design, converge on one, then port steps, runner and cli in order. This is the bottom-right cell of the table.

Not quite

A diamond needs both a known approach and independent pieces, and this has neither.

Check yourself

Which single fact most strongly justifies adding the first diamond?

Pick one

Every option has a reason attached.

That justifies the second diamond

Many modules means a parallel build. It says nothing about whether you know how to build them. With a known approach, many modules call for a plain diamond, or a tree if the reports pile up.

Yes

Uncertainty about the approach is what the first diamond resolves, and multiplication is what makes resolving it worth paying for. Either one alone is weaker: a known approach needs no exploration, and an uncertain choice that affects one module can be fixed by redoing one module.

Goal. Run a full double diamond by prompt: three strategies for the remaining ops, one chosen plan, parallel porters, one review. Then judge whether the first diamond paid for itself.

Each must propose exactly 3 work packages and reply in at most 15 lines.

Then stop, show me notes/ops-plan.md, and wait for my OK.

  4. Read the plan. If you disagree, say so now; this is the cheapest moment to change course. Then run the second diamond.

    OK. Diamond 2, diverge: for each package in notes/ops-plan.md, run the porter agent once per module in that package. Run the packages in parallel. Inside a package, run modules in order and pass each porter the TRAPS and NOTES lines from the previous porter in that package.

Diamond 2, converge: use the reviewer agent on all four modules. If any module gets FAIL, send its FINDINGS verbatim to a new porter call for that module, then review that module again, at most twice.

Finally, append any new trap to Known traps in MIGRATION.md, run python scripts/status.py, and give me a table: module, package, verify runs, reviewer verdict.

  5. Ask the lead to judge its own first diamond, then check the cost.

    Looking back: did the three strategies differ in any way that changed the final plan? If you had skipped diamond 1 and used a plain diamond, what would have gone differently? Answer in 5 lines.
    /usage
What you should see

Three short proposals that disagree mainly on grouping. The by-trap planner will likely pair rotate with resize because both use floor_div (T2). The chosen plan probably takes that grouping, and inside that package the second porter starts with the first one's T2 notes. Four modules end up passing, with a reviewer verdict for each and possibly one FAIL round. The lead's look back will often admit that with T2 already in MIGRATION.md, diamond 1 changed little. That is the right lesson for four ops. Keep the number from /usage; you now know roughly what three read-only explorers cost compared with the build.

Stretch

Rerun only diamond 1 on a question that is genuinely open: "How should pipeline/steps.py's step registry be ported so that pipeline/runner.py stays simple?" Do not build anything. Compare how much the three proposals differ this time. That difference is the signal that the first diamond is earning its cost.

Key takeaway

Pick the shape from two questions. Is the approach uncertain? Does the build split? Two yeses make a double diamond. One yes on the build side makes a diamond. Use a chain when order is forced, a tree when reports overflow one coordinator, and a cycle when quality needs rounds against a checkable bar.
