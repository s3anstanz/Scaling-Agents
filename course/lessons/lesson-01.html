What an agent actually is

An agent is a model, a set of tools, and a loop that keeps going until something says stop. This lesson pins that idea to a real codebase and sets up the project you will grow from one agent to a hundred.

Part oneThe course and the codebase

Over four weeks you will take one job and push it from a single agent to a fleet. Week 1 is one agent, done properly. Week 2 is a small team of three to five. Week 3 is a system of ten to twenty-five, where the shape of the work matters more than any single prompt. Week 4 is scale: a hundred agents, driven by scripts that orchestrate them the way a build system drives compilers.

The job is a migration. Kestrel is a fictional open-source image-processing library written in Python. In the story it has about 240 modules: colour handling, rectangles and coordinates, a dozen families of image operations, file formats, analysis, a pipeline runner and a command-line tool. Its maintainers want a TypeScript version that behaves identically, down to the output bytes.

You will not port 240 modules for real. The practice repo, kestrel-starter, is a 24-module slice of Kestrel with the same structure, the same kinds of dependencies and the same traps. Every lab runs against it for real, at small cost. When the course reaches a hundred agents, you will run ten to twenty cheap workers against the 24 modules and then reason about what changes at 240.

A migration is a good teaching case because it has every property that makes agent work interesting. There are many similar units of work. They depend on each other in a known order. There is an oracle, meaning an independent source of truth: the Python tests define correct behaviour, and the TypeScript port must pass the same tests. And there are traps, places where Python and JavaScript quietly disagree, that a confident model will walk straight into.

Here is the part of the starter you will touch most this week.

PathWhat it is
kestrel/core/, kestrel/ops/, …The Python source. core/ holds errors, mathutil, color, geometry and image; ops/ holds twelve image operations such as blur and crop.
tests/Python tests, mirroring the source: tests/core/test_color.py, tests/ops/test_blur.py.

Part twoChat, workflow, agent

There are three common ways to put a model to work on Kestrel, and the difference between them is a single question: who decides the next step?

ModeWho picks the next stepOn KestrelGood for
ChatYouPaste color.py into a chat, ask for TypeScript, paste the answer into ts/src/core/color.ts, run the tests yourself.One answer you will check by hand.
WorkflowYour codeA script loops over the 24 files in a fixed order, calls the model once per file and writes whatever comes back.Steps you know in advance, repeated many times.
AgentThe modelClaude Code reads color.py, writes color.ts, runs scripts/verify.sh, reads the failure, edits, runs it again.Tasks where the right next step depends on what just happened.

The chat version breaks the moment the first answer is wrong, because you become the loop. The workflow version is predictable and cheap, and it also writes a broken color.ts with total confidence, because nothing in it looks at the test result. The agent version is the only one that can notice its own mistake, since it chooses to run the tests and then reads what they say.

Anthropic's engineering post Building effective agents draws the same line. It describes agents as models using tools in a loop, and it lists the workflow patterns (chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer) that sit between plain chat and a free-running agent. Its central advice is to start with the simplest thing that works. That advice runs through this whole course. Week 4 brings workflows back, with agents inside each step.

Part threeThe loop

Strip away the product and an agent is three parts. The model reads everything in front of it and writes the next message. The tools are actions the model can request: read a file, edit a file, run a shell command. The loop is the harness, Claude Code in our case, that runs the requested tool, appends the result to the conversation and calls the model again.

Each pass around the loop has the same rhythm. Gather context, act, check the result, decide what to do next. The loop ends when the model writes a reply with no tool request in it, or when something outside the model, such as a turn limit or a budget, cuts it off.

Notice where the check sits. It is inside the loop, before the decision. An agent that acts and then decides without checking is a workflow with extra steps. The whole of Week 1 is about making each of these four boxes deliberate: what the agent sees when it gathers context (Lesson 03), what counts as a passing check (Lesson 04), and what makes the loop stop (Lesson 02).

Predict first

You open Claude Code in kestrel-starter and type: run the Python tests and tell me how many pass. How many times does the model get called before you see the answer?

The answer

At least two. The first call reads your request and replies with a tool request, something like Bash: python -m pytest -q. The model cannot run anything itself. Claude Code runs the command, appends the output to the conversation, and calls the model a second time. Only that second call can see the result and write all tests pass. If the first command fails because, say, the virtual environment is not active, you get a third call, a fourth, and so on. Every tool use costs one more trip around the loop.

Part fourAnatomy of a run on Kestrel

Below is a condensed trace of one agent porting the smallest module, kestrel/core/errors.py. That file defines the library's exception classes (KestrelError, FormatError, BoundsError, PipelineError) and a describe function that formats an error as "FormatError: bad header". The trace is illustrative, but every row is the kind of thing you will see in Lab 02.

thinkPort errors.py. Read the source, its tests and the porting rules first.
toolRead: kestrel/core/errors.py
toolRead: tests/core/test_errors.py
toolRead: MIGRATION.md
toolBash: python -m pytest tests/core/test_errors.py -q
resultall passed (the Python side is the reference)
toolWrite: ts/src/core/errors.ts
toolWrite: ts/test/core/errors.test.ts
toolBash: scripts/verify.sh kestrel/core/errors.py
resultexit 1 · describe: expected "FormatError: bad header", received "Error: bad header"
thinkJS subclasses of Error keep name = "Error" unless the constructor sets it. Set this.name from the class.
toolEdit: ts/src/core/errors.ts
toolBash: scripts/verify.sh kestrel/core/errors.py
resultexit 0 · Python passed · TypeScript passed
stopPorted errors.py and its tests; verify.sh passes. Note: Error subclasses must set name.

Read it as a sequence of loop iterations. Each tool row is the model asking for an action. Each result row is Claude Code feeding the outcome back. The model never touched the disk or the shell directly; it wrote requests, and the harness carried them out under the permissions you configured.

Three things in this trace are worth carrying into every later lesson.

  1. Context is assembled, step by step. The model started knowing only your prompt and CLAUDE.md. It chose to read three files. By the end, its context held the source, the tests, the rules and two test outputs. What it reads decides what it can get right.
  2. The check changed the plan. The first verify.sh run failed, and the failure message named the exact problem. Without that run, the agent would have reported success on broken code.
  3. Stopping was the model's choice. It stopped when the check passed. Nothing forced that. Lesson 02 is about stop conditions you control, and Lesson 04 makes this one mechanical.

Part fiveWhat you control

When people say an agent is good or bad, they usually mean the model. In practice you control more of the outcome through the other two parts. For one agent, the levers are these.

  • The model and its effort. --model, /model or "model" in settings, with aliases such as opus, sonnet and haiku. Effort runs from low to max via /effort or --effort.
  • The tools and permissions. Which actions it may take without asking. The starter's .claude/settings.json already allows python -m pytest, npx vitest and anything under scripts/, so labs do not stall on prompts.
  • The context. What it reads before acting: CLAUDE.md, MIGRATION.md, the source and the tests.
  • The loop's exits. What check means done, and what limits end a run that is not getting there.

Weeks 2 to 4 add more agents, and every one of them is still this loop. A team is several loops passing messages. A workflow is code that starts loops and collects their reports. If one loop is sloppy about checks and stopping, a hundred of them are sloppy at a hundred times the cost. That is why the first week spends five lessons on one agent.

Same ideas in code. Everything here also exists in the Claude Agent SDK (claude-agent-sdk for Python, @anthropic-ai/claude-agent-sdk for TypeScript), where the model, tools, turn limit and budget are options on a query call. The labs use the CLI so you can watch the loop happen.

Lab 01 · In Claude Code ~15 min · est. $0.10–$0.50

Goal. Get the starter running, then watch one Claude Code session explore it and count the loop iterations.

  1. Set up the practice project with steps 1 to 3 of the quick start in the course repo's README. You finish inside a folder called kestrel-starter, and the last command reports 142 passed. Came here from the README? This step is already done. No access to the repo? Download the starter with the button on Course home, unzip it, cd kestrel-starter, run the commands in the Setup section of the README.md inside that folder, then run python -m pytest -q.

  2. Look at the work before any agent does. The first command prints the dependency waves; the second ends with 0/24 modules ported.

    python scripts/deps.py --layers
python scripts/status.py

  3. Start Claude Code in the repo root.

    claude

  4. Type this prompt. As it runs, count the tool calls. Each one is a trip around the loop.

    Explain this repository in under 200 words: what Kestrel is, where the Python and TypeScript code live, and what counts as a ported module. Then run python scripts/deps.py --layers and tell me which modules can be ported first, and why. Do not edit any files.

  5. Now ask it to run the exit condition on a module that has not been ported yet.

    Run scripts/verify.sh kestrel/core/errors.py and explain in two sentences what its exit code means right now.

  6. Check what the session cost, then quit with /exit or Ctrl+D.

    /usage
What you should see

For the first prompt, a handful of tool calls (reads of CLAUDE.md or MIGRATION.md, a directory listing, the deps.py run), then a summary that names core/errors and core/mathutil as wave L0 because they import nothing else in Kestrel, with the 14-module wave L3 and a single cli at L6. For the second, usually one Bash call (approve it if Claude adds ; echo $?): the Python tests pass, then verify.sh fails with TS port missing and exits 1, because nothing is ported yet. /usage shows a cost in cents. Write down your count of tool calls for each prompt; you will compare against headless runs next lesson.

Stretch

Ask the same first question in a fresh session started with claude --model haiku. Does it make the same tool calls in the same order? Different models plan different loops for the same task, and that difference shows up in cost long before it shows up in quality.

Key takeaway

An agent is a model choosing tool calls inside a loop, with each result fed back before the next choice. What it reads, how it checks, and when it stops are yours to design.
