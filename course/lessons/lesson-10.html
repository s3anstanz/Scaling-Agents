Loops between agents

In Week 1 you engineered one agent's loop. Now the loop runs between two agents: a porter that writes and a reviewer that judges. This lesson covers what makes that loop converge, what makes it bounce forever, and how to stop it either way.

Part oneWhy a second loop

The porter already loops. It runs scripts/verify.sh, reads the failure, fixes the code and runs it again until the script exits 0. So why put a reviewer after it?

Because verify.sh only knows what the tests know. If the porter ports seven of eight Python tests, the script happily passes the seven. If the porter edits an expected value, the script passes the edited test. If the code uses a bare % on a path no test exercises, nothing fails. Tests are an excellent oracle for what they cover and silent about everything else.

Anthropic's "Building effective agents" calls the fix the evaluator-optimizer pattern. One model produces a result, a second model evaluates it against criteria and sends feedback, and the first model revises. On Kestrel the optimizer is the porter and the evaluator is the reviewer you defined in Lesson 08, with its rubric R1 to R5.

You now have three loops stacked inside each other. The innermost is the porter against verify.sh, which is mechanical and fast. The middle one is porter against reviewer, which is judgement and slower. The outermost is your Stop hook from Lesson 04, which keeps the whole session from finishing while any ported module fails. Each loop needs its own stop conditions.

Part twoFour things that make it converge

A loop between agents converges when each round moves it closer to a pass and it ends in a bounded number of rounds. Four design choices make that happen.

1. A checkable rubric. "Is this a good port?" never converges, because two models can disagree about "good" forever. "Does every Python test in tests/ops/test_pad.py have a TS counterpart, and what are the two counts?" converges, because it has an answer. Every reviewer item should be pass or fail with one line of evidence. That is why reviewer.md asks for file:line or command output on each of R1 to R5.

2. A maximum number of rounds. A round is one porter call plus one reviewer call. Three rounds is a sensible cap for one Kestrel module. If three rounds have not produced a pass, the problem is usually missing information, and a fourth round just costs another two calls. The cap is the turn-cap stop condition from Lesson 02, applied to the outer loop.

3. Progress detection. Compare each round's failing checks with the previous round's. Different findings mean the loop is moving: the porter fixed one thing and the reviewer found the next. The same failing check at the same place twice in a row means the loop is stuck. Stop and escalate to a person with both reports. This is the no-progress stop condition, and it catches the expensive case early.

4. An independent reviewer. Independence has two parts. A fresh context: start a new reviewer call each round and give it only the module path and the rubric. Do not forward the porter's explanation, because a reviewer that reads "the % is fine, inputs are always positive" tends to agree. A different model: your porter runs on Sonnet or Haiku and your reviewer on Opus. Two copies of the same model with the same context tend to make the same mistakes and approve each other's work.

Predict first

Suppose the lead forwards each porter report to the reviewer along with the module path, to "save it some time". The porter's NOTES line says: "Used plain % in wrap mode; offsets are non-negative in practice." The tests pass. What does the reviewer most likely do with R3?

The answer

It most likely passes R3. The porter's claim arrives as context, it sounds reasonable, and the tests are green, so the reviewer inherits the porter's blind spot. A reviewer that sees only the code, the Python original and MIGRATION.md has to check for itself whether an offset can be negative, and in pad's wrap mode it can. That check is trap T3: Python's -1 % 5 is 4, JavaScript's is -1. Saving the reviewer time this way removes the reason it exists.

Part threeThree rounds on ops/pad.py

Here is a loop that converges, round by round. The details are illustrative; your run will differ, and that is fine. Watch how each round's findings change, which is the signal that the loop is making progress.

Step through it
  1. Round 1. The lead starts a porter call with one line: kestrel/ops/pad.py. Everything else the porter needs is in porter.md and MIGRATION.md.
  2. The porter writes pad.ts with a plain i % n for wrap mode. It ports seven of the eight Python tests and skips the one with a negative offset. verify.sh exits 0. Its report says VERIFY: pass.
  3. A fresh reviewer call on Opus gets the module path only. R1 passes. R2 fails: 8 Python tests, 7 TS tests, test_wrap_negative missing. R3 fails: bare % in the x-axis wrap. VERDICT: FAIL.
  4. Round 2. The lead passes the FINDINGS verbatim to a new porter call. The porter adds the missing test, which fails with -1 where Python gives 4. That is T3. It changes the x-axis wrap to ((i % n) + n) % n and verify.sh passes.
  5. A new reviewer call: R2 now passes, but R3 still fails, this time on the y-axis wrap, which uses the same bare %. No test covers it. The failing check is the same, but the location and finding are new, so the loop is making progress. Continue.
  6. Round 3. The porter fixes the y-axis wrap and adds a test for a negative y offset. Extra TS tests are fine; R2 only requires that every Python test has a match.
  7. The reviewer passes R1 to R5. VERDICT: PASS goes back to the lead. Three rounds, inside the cap.
  8. The lead, the only writer of MIGRATION.md, appends T3 to Known traps with the fix pattern. The next agent that meets % on a possibly negative value starts with the answer.

Notice what the tests alone would have shipped: a passing pad.ts with a T3 bug on both axes. The first round's verify.sh pass was true and useless. The reviewer earned its cost by checking coverage and trap patterns, which are the two things a test suite cannot check about itself.

Part fourHow loops between agents fail

The most common failure has a name: ping-pong. The reviewer asks for A, the porter does A, the next reviewer asks for B, which undoes A, and around it goes. It happens when the rubric leaves room for taste. Two fresh reviewer calls can reasonably prefer different import styles, and the porter faithfully alternates between them.

FailureWhat you seeFix
Ping-pongFindings alternate between two states; the code flips back and forthRubric items come only from MIGRATION.md and the tests. Same failing check twice: escalate.
Rubber stampPASS on every round 1, including ports with gapsDifferent model, fresh context, and evidence required on every rubric line
Moving goalpostsEach round brings new minor findings; three rounds never reach PASSOnly R1 to R5 can fail a port. Style comments go in a note and never fail a port.
Gaming the oracleTests pass after the porter changed an expected valueThe porter's rule against it, plus R2 comparing values against the Python tests
Endless loopRounds keep going because no one counts themThe lead counts rounds and stops at 3, whatever the latest verdict says

Most of these are fixed ahead of time, in the role files and in the lead's loop prompt.

Here is what a converging loop on analysis/stats.py looks like from the lead's seat. It is illustrative, and shorter than pad.

toolAgent (porter): kestrel/analysis/stats.py
resultVERIFY: pass · RUNS: 2 · TRAPS: none
toolAgent (reviewer): kestrel/analysis/stats.py, rubric R1–R5
resultVERDICT: FAIL · R3 fail: ts/src/analysis/stats.ts median() calls values.sort() with no comparator; [10, 9, 100] sorts as [10, 100, 9]
thinkRound 1 of 3. New finding. Forward FINDINGS verbatim to a new porter call.
toolAgent (porter): kestrel/analysis/stats.py + reviewer FINDINGS
resultVERIFY: pass · RUNS: 2 · TRAPS: T4 numeric sort needs (a, b) => a - b; added a test with [10, 9, 100]
toolAgent (reviewer): kestrel/analysis/stats.py, rubric R1–R5
resultVERDICT: PASS
toolEdit: MIGRATION.md (Known traps: T4)
stopStop hook runs scripts/stop_gate.py: all ported modules pass. Session ends.
Check yourself

Round 2's reviewer reports the same R3 failure as round 1, at the same line of pad.ts, with the same explanation. The cap is three rounds. What should the lead do?

Pick one

Every option has a reason attached.

Not this one

The cap is a ceiling, and reaching it is never the goal. An identical failure means the porter did not or could not act on the finding. A third round with the same inputs will most likely produce the same output and cost two more calls.

Yes

No progress is a stop condition in its own right. Something is missing that neither agent can supply: maybe the finding is wrong, or the porter misreads it, or MIGRATION.md is silent on the case. A person reading both reports can usually tell which in a minute.

Not this one

The reviewer has no edit tools, by design. If it could fix things, nobody would review its fix, and the loop would lose its independent judge.

Not this one

Shopping for a friendlier reviewer turns the evaluator into a rubber stamp. If you doubt the finding, that doubt is itself a reason to escalate.

Part fiveMaking a subagent's "done" mechanical

In Lesson 04 the Stop hook made the lead's "done" mechanical: when Claude tries to finish, your script runs, and exit code 2 sends it back to work. Claude Code has the same hook for subagents, called SubagentStop. It runs when a subagent tries to finish, and its input JSON includes agent_type, so your script can act only for the porter and let the planner and reviewer finish freely. The same rules apply as for Stop: check stop_hook_active to avoid an endless block, and remember that Claude Code caps consecutive stop-hook continuations at 8.

Annotations

Click a marked line. This is the lab's stretch configuration.

Line 3 · the lead's gate

Your Lesson 04 hook, unchanged. It guards the outermost loop: the session cannot end while a ported module fails.

Line 6 · the subagent's gate

Same shape as Stop, fired when any subagent tries to finish. The script receives agent_type and should exit 0 at once for anything other than porter.

Line 7 · scope the check

Be careful what the porter's gate checks. If it reruns all of status.py --json like stop_gate.py does, a porter can be blocked by another porter's half-finished module during a parallel run. With parallel porters, keep the repo-wide check at the lead and let the porter's own verify.sh loop and the reviewer carry the rest.

Lab 10 · In Claude Code ~20 min · est. $1.50–$4.00

Goal. Run a bounded porter and reviewer loop, at most 3 rounds with no-progress detection, on ops/pad.py (trap T3) and analysis/stats.py (trap T4).

  1. Confirm both modules are ready. analysis/stats needs ops/histogram, which you ported in Lab 09.

    source .venv/bin/activate
python scripts/status.py --next

  2. Start the lead.

    claude --model opus

  3. Give it the loop rules. Every stop condition from this lesson is written into the prompt.

    Port kestrel/ops/pad.py with a porter/reviewer loop. Rules:

- A round is: one porter agent call, then one new reviewer agent call.
- Give the reviewer only the module path and ask it to apply its rubric R1-R5. Do not pass it the porter's report or explanation.
- If the reviewer returns VERDICT: PASS, the loop ends with success.
- If it returns FAIL, pass its FINDINGS verbatim to a new porter call. That starts the next round.
- Maximum 3 rounds.
- No-progress rule: if the reviewer reports the same failing check at the same location in two consecutive rounds, stop early and show me both reports instead of starting another round.

When the loop ends, append any new trap to Known traps in MIGRATION.md (you are the only writer of that file) and print a table: round, porter RUNS, verdict, failing checks.

Then run the same loop for kestrel/analysis/stats.py.

  4. Check the state of the port and the cost.

    python scripts/status.py
    /usage
What you should see

Two round tables. pad often needs two or three rounds; look for T3 in a porter TRAPS line or a reviewer R3 finding about %. stats often fails R3 once on .sort() without a comparator (T4) and passes in round 2. If either loop stops on the no-progress rule, read the two reports yourself: that is the escalation working. By the end MIGRATION.md should list T3 and T4, and status.py should show every op, both io modules and analysis/stats ported and passing. Week 3 starts from here.

Stretch

Ask Claude to write scripts/subagent_gate.py, modeled on scripts/stop_gate.py: read the hook JSON from stdin, exit 0 if stop_hook_active is true or agent_type is not porter, otherwise run python scripts/status.py --json and exit 2 with the failures on stderr. Add the SubagentStop block above to .claude/settings.local.json, start a fresh session, and port analysis/edges.py with a single porter. Then think about what this gate would do to three porters running in parallel.

Key takeaway

A loop between agents converges when the rubric is checkable, rounds are capped, a repeated failure triggers escalation, and the reviewer sees the work with fresh context and a different model. Without those, two agents can argue forever on your budget.
