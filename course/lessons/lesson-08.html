Lesson 08 Week 2 · Small teams ~16 min 3–5 agents

Defining subagent roles

So far every worker was an anonymous helper described in a prompt. Here you write three named roles as files (planner, porter and reviewer), each with its own instructions, tools and model, and use them to port io/.

Part oneFrom a long prompt to a role file

Look back at your prompts from Labs 06 and 07. Half of each one repeated the same rules: follow MIGRATION.md, run scripts/verify.sh until it exits 0, reply in five lines with MODULE, VERIFY, RUNS, TRAPS and FILES. Those rules describe a role. Every porter needs them, whatever module it gets.

Claude Code lets you write a role down once as a subagent file. Project roles live in .claude/agents/*.md, which the starter left empty for this lesson. Personal roles you want in every project go in ~/.claude/agents/. For a one-off session you can also pass definitions as JSON with --agents.

A subagent file has two parts. The frontmatter, between the two --- lines, holds settings in YAML. The body below it becomes the subagent's system prompt. When the lead delegates, the subagent starts with that system prompt, the delegation message and your CLAUDE.md. It still does not see the lead's conversation, so the body has to carry everything the role always needs, and the delegation message carries only what changes per task: usually just the module path.

Writing roles as files buys four things. The rules stop drifting between prompts. They live in git, so you can review a change to the porter like any code change. Tool limits become enforced settings instead of polite requests. And the model for each role is fixed where the role is defined.

Part twoThe fields that matter

Two fields are required. name is how you and the lead refer to the role. description is how the lead decides when to use it. The lead reads every description and delegates when a task matches, so a description is closer to a routing rule than to documentation. Say what the role does, when to use it and what it returns. The phrase "use proactively" encourages the lead to delegate without being asked.

Four optional fields do most of the work on Kestrel:

  • tools is an allowlist. The role gets these tools and no others. Leave it out and the role gets the full toolset.
  • model sets the role's model (precedence level 2 from Lesson 07). Use inherit to follow the main model.
  • effort sets thinking effort for the role.
  • maxTurns caps the role's loop. It is the turn-cap stop condition from Lesson 02, now built into the role.

Other fields exist for later lessons: disallowedTools, permissionMode, skills, mcpServers, hooks, memory, background, color, initialPrompt, and isolation: worktree, which you will use in Lesson 14 to keep parallel porters out of each other's files.

You can call a role three ways. Mention it with @agent-porter. Ask in plain words, as in "use the porter agent to port ops/contrast.py". Or run a whole session as that role with claude --agent porter.

Annotations
Click a marked line. Every rule here used to be pasted into a prompt.

        
Line 1 · frontmatter
Settings sit between the two --- lines. Everything after line 8 is the system prompt.

        
Line 3 · description
The lead routes on this text. It names the trigger ("port kestrel/...py"), the scope (one module per call) and the exit condition. "Use proactively" makes delegation the default for matching tasks.

        
Line 4 · tools
An allowlist. The porter must write files and run verify.sh, so it gets Edit, Write and Bash. It gets nothing else, such as the Agent tool, so it cannot spawn helpers of its own.

        
Line 5 · model
Set this from your Lab 07 data. Frontmatter outranks CLAUDE_CODE_SUBAGENT_MODEL, so once this line exists the environment variable no longer applies to porters. A per-call model still overrides it.

        
Line 7 · maxTurns
A hard turn cap per delegation. Thirty turns is generous for one Kestrel module; a porter that needs more is stuck, and you want it back with a report.

        
Line 14 · reuse
Without this, porters copy a private floorDiv into every file that needs one. Each copy is another place for trap T2 to come back.

        
Line 18 · protect the oracle
A cheap model under pressure sometimes "fixes" a T1 failure by editing the expected value. This line forbids it, and the reviewer checks it.

        
Line 19 · the barrel
The starter's convention: every ported module adds one export line. It is also the shared-file hotspot that Lesson 14 redesigns.

        
Line 24 · no-progress stop
The fourth stop condition from Lesson 02. The same failure three times means the porter lacks information, so more attempts only burn tokens.

        
Line 26 · single writer
MIGRATION.md is shared by every agent. Porters report traps; only the lead appends them. Lesson 12 explains this rule in depth.

        
Line 28 · the report
The only thing that crosses back to the lead. A fixed shape makes reports comparable and keeps traps from being lost in a lossy handoff.

      

    

  


  
Part threeLeast privilege, role by role

  
Least privilege means each role gets the smallest set of tools that lets it do its job. On a team it does two things. It limits the damage a confused agent can do, and it keeps each role honest about what it is for.

  

    
RoleToolsEdits files?ModelReturns

    
      
plannerRead, Grep, Glob, BashNeverinherit, high effortA plan in a fixed shape

      
porterRead, Grep, Glob, Edit, Write, BashIts own module, its test, one barrel linesonnet or haikuThe 6-line report

      
reviewerRead, Grep, Glob, BashNeveropus, high effortVERDICT: PASS or FAIL with findings

    
  

  
Two read-only roles and one writer. The planner and reviewer keep Bash so they can run scripts and tests.

  
The reviewer never edits, and this is the rule people most want to break. If the reviewer could fix "small things", two problems follow. First, nobody reviews the fix. Second, the reviewer starts adjusting tests until they pass, which is the exact failure it exists to catch. A reviewer that only reads, runs tests and reports stays independent.

  
Bash needs one more sentence. It is a single tool, so a role either has it or not. What a planner or reviewer actually runs through Bash is shaped by its prompt ("only run these scripts") and limited by your permission settings. The starter's .claude/settings.json allows python -m pytest, npx vitest, scripts/* and python scripts/* without asking. Anything else prompts you, which is what you want from a read-only role.


  

  

    
Predict first

    

      
Suppose you write the porter's description as "Helps with TypeScript code." Then you type "port kestrel/io/pgm.py" without naming an agent. What does the lead do?

      

      

        
The answer

        
Probably it ports the module itself, in its own context, with none of the porter's rules, tools or model. It might delegate, but nothing in "Helps with TypeScript code" tells it this task is the porter's job. The lead routes on descriptions. A description that names the trigger ("port kestrel/...py"), the scope and the result makes delegation reliable; a vague one makes it a coin toss. When it matters, name the agent explicitly.

Goal. Write the planner, porter and reviewer roles, then use them to port io/ppm and io/pgm with a review step.

      
    
        
  1. Create the planner.
    
          
    ---
name: planner
description: Read-only planner for the Kestrel port. Use before porting a group of modules, to split work into independent packages, or to propose a porting strategy. Never edits files. Returns a plan in a fixed shape.
tools: Read, Grep, Glob, Bash
model: inherit
effort: high
maxTurns: 15
---
You plan work for the Kestrel Python-to-TypeScript port. You never write or edit files. Your reply is the plan.

Ground every plan in the repo. Run only these commands, and otherwise just read files:
- python scripts/status.py
- python scripts/status.py --next
- python scripts/deps.py --layers

Read MIGRATION.md, including Known traps. Scan the Python modules in scope for the patterns the traps describe: round(, //, %, sorted( or .sort(, and header parsing.

If the delegation message gives you a lens or strategy, plan through that lens and say what it costs.

Reply in this shape, at most 25 lines:
SCOPE: modules in scope; any that are not ready yet, and why
PACKAGES: numbered; each is a set of modules one porter can do alone, with all its dependencies already ported
TRAPS: per package, the known traps that apply and anything that looks like a new one
ORDER: what must run first and what can run in parallel
VERIFY: the exact scripts/verify.sh commands
RISKS: at most 3
    
        
    2. 
        
  2. Create the porter. It is the file you just studied.
    
          
    ---
name: porter
description: Ports exactly one Kestrel Python module and its tests to TypeScript, then loops on scripts/verify.sh until it passes. Use proactively for any "port kestrel/<path>.py" task, one module per call.
tools: Read, Grep, Glob, Edit, Write, Bash
model: sonnet
effort: medium
maxTurns: 30
---
You port one Kestrel module from Python to TypeScript. The delegation message names it, for example kestrel/ops/pad.py.

Before you write code:
1. Read MIGRATION.md in full, including Known traps.
2. Read kestrel/<path>.py and its tests in tests/<dir>/test_<name>.py.
3. Read the ported TypeScript of every module it imports, under ts/src/. Import from those files. Do not re-implement helpers that already exist there.

Write:
- ts/src/<path>.ts and ts/test/<path>.test.ts.
- Every Python test, with the same inputs and expected values. Never change an expected value to make a test pass.
- One line in ts/src/index.ts: export * from "./<path>"; unless it is already there.

Loop:
- Run scripts/verify.sh kestrel/<path>.py. Read the failure, fix the code, run it again.
- Stop when it exits 0.
- If the same failure appears on three runs in a row, stop and report it.

Touch nothing else. Do not edit MIGRATION.md or other modules; report traps instead.

Final report, at most 8 lines:
MODULE: kestrel/<path>.py
VERIFY: pass or fail (last exit code)
RUNS: number of verify.sh runs
TRAPS: each trap hit, as "T<n>: one line" or "new: one line"
FILES: files written or edited
NOTES: anything the lead must decide
    
        
    3. 
        
  3. Create the reviewer. Its rubric (R1 to R5) is what Lesson 10's loop runs against.
    
          
    ---
name: reviewer
description: Independent reviewer for ported Kestrel modules. Use after a porter finishes, giving it the module path or paths. Runs the tests and checks the port against MIGRATION.md. Never edits files. Returns VERDICT PASS or FAIL with findings.
tools: Read, Grep, Glob, Bash
model: opus
effort: high
maxTurns: 15
---
You review ported Kestrel modules. You did not write them and you do not fix them. When something is wrong, say exactly what and where; the porter fixes it.

Run only scripts/verify.sh and python scripts/status.py, and otherwise just read files.

For each module kestrel/<path>.py, check:
R1 Tests: run scripts/verify.sh kestrel/<path>.py. Pass only on exit 0.
R2 Coverage: every test function in the Python test file has a matching TS test in ts/test/<path>.test.ts with the same inputs and expected values. Give both counts.
R3 Traps: for every entry in MIGRATION.md Known traps, check the TS code. Flag Math.round where Python used round(), Math.trunc or plain / where Python used //, a bare % whose left side can be negative, .sort() on numbers without a comparator, and header parsing that ignores # comments or irregular whitespace.
R4 Contract: names and types follow MIGRATION.md; helpers are imported from already-ported modules, not copied.
R5 Barrel: ts/src/index.ts has exactly one export line for the module.

Reply in exactly this shape:
VERDICT: PASS or FAIL
R1: pass or fail, one line of evidence
R2: pass or fail, one line of evidence
R3: pass or fail, one line of evidence
R4: pass or fail, one line of evidence
R5: pass or fail, one line of evidence
FINDINGS: on FAIL only, numbered; each gives file:line, the check that failed, and the fix in one sentence

What you should see
The planner replies with SCOPE, PACKAGES, TRAPS, ORDER, VERIFY and RISKS, and probably flags header parsing in ppm.py. Two porter calls run in parallel and each returns the 6-line report. io/ppm is where trap T5 lives: PPM headers may contain # comments and irregular whitespace. A naive split on spaces fails the Python-derived tests; if the porter misses part of it, the reviewer's R3 should catch it. You end with io/ppm and io/pgm passing, a T5 entry in MIGRATION.md written by the lead, and three agent files that Week 3 builds on.

      
Stretch
Run claude --agent reviewer and ask it to review kestrel/ops/blur.py from Week 1. A whole session in the reviewer role sees your port with fresh eyes. Then ask it to "just fix" a finding and watch the tool allowlist stop it.

    

  


  
Key takeaway
A role file turns repeated prompt text into an enforced contract: a description that routes, a tool allowlist that limits, a model and turn cap that budget, and a report shape that survives the handoff. Give each role the least it needs, and never let the reviewer edit.
