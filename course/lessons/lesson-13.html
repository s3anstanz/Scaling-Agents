Who talks to whom

The graph shape from Lesson 9 says which work depends on which. Communication topology says which agents can send messages to which. It is a separate choice, and it sets most of your coordination cost.

Part oneShape of the work, shape of the talk

In Lesson 11 the work had a clear shape: a DAG in seven waves. That says nothing about how agents exchange information while they do it. Two systems with the same work graph can have very different conversations. In one, every porter reports only to the orchestrator. In another, porters talk to each other directly, and the orchestrator mostly listens.

The pattern of who can talk to whom is the communication topology. You will meet four of them in practice. Each one is a trade between how much information moves and how much it costs to move it.

Part twoThe four topologies

Hub-and-spoke. One orchestrator in the middle, workers around it, and every message goes through the middle. This is what Claude Code subagents give you. A subagent receives one delegation message from its parent and sends back one final report. It cannot see or message its siblings. Everything you did in Lesson 11 was hub-and-spoke. The hub is simple and easy to reason about, and it is also the bottleneck: every report lands in one context window.

Hierarchy. A tree of hubs. The lead talks to a few sub-leads, and each sub-lead runs its own workers. Claude Code subagents can spawn subagents, up to 3 layers deep by default (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH), and up to 20 run at once by default (CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS). Each level summarizes before passing information up, which keeps the lead's context small and loses detail at every step. Week 4 builds a hierarchy for Kestrel-240.

Mesh. Any agent can message any other directly. Claude Code's agent teams work this way: teammates message each other by name and share a task list. A mesh moves information fastest between the two agents who need it, without a trip through the lead. It is also the most expensive shape, for a reason you can count.

Blackboard. Nobody sends messages. Agents read and write a shared surface, which for Kestrel means files: the repo, results/, MIGRATION.md, PLAN.md. Lesson 12 used it with the single-writer rule. In practice it runs underneath the other three. Even a hub-and-spoke system shares the repo.

Part threeCounting channels

A channel is a pair of agents that can talk to each other. A hub with n agents has n − 1 channels, one from the hub to each worker. A full mesh has a channel between every pair: n(n − 1)/2.

Predict first

A lead plus 9 teammates, all able to message each other, makes 10 agents. How many channels is that? How many would the same 10 agents have as hub-and-spoke?

The answer

Mesh: 10 × 9 / 2 = 45 channels. Hub-and-spoke: 9. Each channel is a place where a message can be sent, read, misread and answered, and every read costs tokens in somebody's context. Five times the channels does not guarantee five times the messages, but it allows them, and agents asked to coordinate tend to use the channels they have.

Hub channels grow in a straight line. Mesh channels grow with the square. This is why the docs suggest starting agent teams at 3–5 teammates, and why nobody runs a 100-agent mesh.

Part fiveAgent teams (experimental)

Experimental. Agent teams are off by default and marked experimental. The details below are current as of this course, and they may change. Check the Claude Code docs before you build anything lasting on them.

Turn teams on by setting CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1, either in your shell or in the env block of settings.json. Your main session becomes the team lead. When you ask it for a team, it starts teammates, which are separate Claude Code instances, each with its own context window. Two things make a team different from a set of subagents.

  1. Teammates can message each other by name. A subagent can only report to its parent.
  2. The team shares a task list. Each task has a status, and tasks can depend on other tasks, so a blocked task stays blocked until its dependency is complete.

Some limits apply. A session can run one team. Teams cannot be nested. Teams do not work in -p headless mode or through the Agent SDK. Three hooks fire on team events: TeammateIdle, TaskCreated and TaskCompleted. You could, for example, attach a TaskCompleted hook that runs scripts/verify.sh for the module the task named, much as your Stop hook does.

Cost is the main thing to plan around. The Claude Code costs page notes that teams use roughly 7x the tokens of a single session when teammates run in plan mode. Every teammate carries its own full context, and every message is read by someone.

So when does a mesh pay for itself? When workers must settle something with each other in the middle of their work, and routing every question through the lead would be slower and lossier. On Kestrel, the twelve ops do not need to talk; each depends only on finished core modules. The pipeline chain is different. runner calls functions in steps, and cli calls runner. Whoever ports runner needs to know exactly what the steps port will export, and the cheapest way to find out is to ask the steps teammate directly.

Make the call

Imagine starting Kestrel's wave L3 from scratch. Which setup do you choose?

The situation
  1. 14 modules: twelve ops plus io/ppm and io/pgm.
  2. All of them depend only on core/*, which is ported and passing.
  3. None imports another module in the same wave.
  4. Known traps are written in MIGRATION.md.

Decide, then see the reasoning.

Right call

The modules are independent and the shared context is already in a file. Nobody has anything to negotiate, so a mesh would add channels with nothing to carry. Hub-and-spoke with a contract does it at a fraction of the tokens, and 14 is under the default of 20 concurrent subagents.

Not quite

The docs suggest 3–5 teammates, and this wave wants 14. Even at 5, teammates would have nothing to say to each other, and you would pay around 7x the tokens for the ability to say it. Teams earn their cost on coupled work.

Lab 13 · In Claude Code (experimental feature) ~25 min · est. $3.00–$10.00

Goal. Port the pipeline chain (steps, runner, cli) with a lead and three teammates who settle interfaces by message, then compare cost and outcome with Lesson 11's hub-and-spoke run.

  1. Confirm where you are. Only the pipeline chain should be left.

    source .venv/bin/activate
python scripts/status.py --next

  2. Start a session with teams enabled. The variable applies only to this launch.

    CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude --model opus

  3. Ask the lead for the team. The single-writer rule from Lesson 12 still holds: only the lead touches the barrel and MIGRATION.md.

    Create an agent team with three teammates named steps, runner and cli. Put three tasks on the shared task list:
1. Port kestrel/pipeline/steps.py and its tests. Owner: steps.
2. Port kestrel/pipeline/runner.py and its tests. Owner: runner. Depends on task 1.
3. Port kestrel/cli.py and its tests. Owner: cli. Depends on task 2.
Rules for every teammate: follow MIGRATION.md. A task is complete only when scripts/verify.sh on its Python module exits 0. Only the lead edits ts/src/index.ts and MIGRATION.md; send the lead your export line and any new trap. While your task is blocked, read your Python module and its tests, then message the teammate upstream of you to agree the exact TypeScript names and signatures you will import. Keep messages short and about interfaces only. Report to the lead when your task completes. The cli teammate must make ts/src/cli.ts runnable as `npx tsx src/cli.ts <in> <out> "<spec>"` from inside ts/, with the same exit codes as kestrel/cli.py, because scripts/difftest.py calls it that way.

  4. Watch the messages. Look for the moment runner asks steps how a step is represented, and note whether the answer changes anything in steps. When all three tasks are complete, check the repo and the bill.

    /usage
    python scripts/status.py

  5. Ask the lead for a retrospective, then add a line under the table in notes/baseline.md with modules, cost, wall-clock and message count, beside your Lesson 11 line.

    Summarize the team run: how many messages did teammates send each other, what did they agree on, and did any message prevent a mismatch between steps, runner and cli before code was written? Then estimate whether a hub-and-spoke run with porter subagents in sequence would have cost more or less for these three modules, and why.
What you should see

The runner and cli tasks show as blocked at first, and those teammates read Python and send interface questions while they wait. When steps finishes, runner starts, then cli. status.py ends with all 24 modules ported and passing. Cost per module will be well above your Lesson 11 subagent run; whether the interface talk earned that back is the judgment this lab is for. If agent teams are unavailable in your version, run the same three tasks in order with your porter subagent instead (one at a time, since each depends on the last), so the pipeline is ported before Lesson 15.

Stretch

Add a TaskCompleted hook in .claude/settings.local.json that runs python scripts/status.py and logs its output, so every task completion leaves a measured record next to the teammate's claim.

Key takeaway

Choose who talks to whom on purpose. Hub-and-spoke and files cover independent work cheaply; a mesh earns its square-law cost only when workers must settle something with each other mid-task, as adjacent pipeline modules do.
