Lesson 06 Week 2 · Small teams ~15 min 3–5 agents

Why split, and what it costs

A second agent is a design decision with a price tag. This lesson names the four things a split buys and the three things it costs, then you run your first three-agent port and hold it up against your Week 1 baseline.

Part oneThe first time the work invites a team

In Week 1 you ported core/errors, core/mathutil, core/color, core/geometry, core/image and ops/blur with one agent. That agent had a bounded loop, a context file in MIGRATION.md, a Stop hook that refuses "done" while a ported module fails its tests, and a cost cap. Your notes/baseline.md holds the turns, cost and wall-clock time for each module.

One agent was the right call for that stretch because the modules came in a strict order. color needs mathutil. image needs color and geometry. Nothing could run side by side, so a second agent would only have waited.

Run python scripts/status.py --next today and the picture changes. With image ported, every module in wave L3 is ready: the twelve ops plus io/ppm and io/pgm. You have done one of them (blur). Thirteen modules are now waiting, and none of them depends on another. This is the first point in the port where the shape of the work allows more than one agent to make progress at the same time.

Some vocabulary before we go on. The lead is your main Claude Code session, the one you type into. A subagent is a separate Claude instance the lead starts with its Agent tool. The subagent gets a fresh context: its own system prompt, the delegation message the lead wrote for it, and your CLAUDE.md. It does not see the lead's conversation. When it finishes, only its final report comes back to the lead. Everything else it read and did stays behind.

That last sentence drives most of this week. Keep it in mind.

Part twoFour reasons to split

There are four good reasons to hand work to another agent. Any one of them can justify a split. A split that has none of them is just a more expensive way to do the same thing.

1. Context isolation. A porter for ops/crop.py needs to read crop.py, tests/ops/test_crop.py, ts/src/core/image.ts and MIGRATION.md. It never needs the forty tool results produced while porting flip. In Lesson 03 you saw that the context window is the agent's working memory and that it degrades as it fills. Splitting gives each piece of work a clean desk. The lead's desk stays clean too: it receives three short reports instead of three piles of test output.

2. Parallelism. invert, flip and crop are independent leaves of the dependency graph. Run them at once and the wall-clock time is roughly the slowest of the three, plus the lead's overhead, instead of their sum. By default Claude Code runs up to 20 subagents concurrently (CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS), so three is nowhere near a limit.

3. Specialization. Each subagent can have its own instructions, its own tool list and its own model. A porter needs to edit files. A reviewer should not. A planner can run on a stronger model than the workers it plans for. You will build these roles in Lessons 07 and 08.

4. Independent judgement. The agent that wrote the code is the worst judge of it. It remembers why it made each choice, so it reads its own intent into the code. A reviewer with a fresh context sees only the code and the tests. That is the reviewer who notices Math.round where Python used banker's rounding (trap T1). Lesson 10 builds that loop.

Part threeThree things a split costs

Tokens. Anthropic's write-up of its multi-agent research system gives two numbers worth carrying around. A single agent uses about 4 times the tokens of a chat. A multi-agent system uses about 15 times. The same post reports that a lead agent with parallel subagents beat a single agent by 90.2% on their internal research eval, and that token usage alone explained about 80% of the performance variance on their browsing eval. Read those together. Teams often do better partly because they spend more, and you pay for every token. On Kestrel the duplication is easy to see: each porter rereads MIGRATION.md, CLAUDE.md and image.ts on its own. Shared context is paid for once per agent.

Coordination overhead. Somebody writes three briefs, waits for the slowest worker, reads three reports and settles anything that collides. Collisions are real in this repo. Every ported module adds one export * from line to ts/src/index.ts, so three porters working in one folder all edit the same file. The lead pays for that coordination in its own turns and tokens.

Lossy handoffs. Only the final report returns. Suppose the crop worker discovers that a negative box offset goes through floor_div and therefore hits trap T2. If its report does not mention that, the lead never learns it, and neither does the next agent that ports a module using floor_div. Discoveries die with the worker's context unless the report format asks for them. That is why the lab's prompt asks each worker to name any trap it hit.

There is one more cost, and it is the one that matters most for a migration. The same Anthropic post says multi-agent systems fit poorly when agents need shared context or have many dependencies between them, and that this includes most coding tasks. Kestrel is a coding task. You can parallelize it only where the dependency graph says the pieces are independent. Today you picked three leaves of that graph, which is the easy case. Lesson 11 turns this into a method: find the graph first, then decide how many agents it can feed.

Predict first

Look at your baseline for ops/blur. Now picture the lab run: three subagents port invert, flip and crop at the same time. Compared with three single-agent ports one after another, what happens to total wall-clock time, and what happens to cost per module?

The answer

Wall-clock time should drop to roughly the slowest single port plus a few minutes of lead overhead for briefing and reading reports. Cost per module usually stays flat or rises. Each worker rebuilds the same context from scratch, and the lead spends tokens coordinating. These three ops are small, so the overhead is a large share of the total. If your baseline ports were already quick, the parallel run can save less time than you expect. Write your guess down and check it against /usage at the end of the lab.

Part fourWhere the curve bends

If three agents help, why not thirteen, one per ready module? Two forces push back. First, the work has an order. Kestrel's 24 modules sit in 7 waves, and no number of agents lets you port runner before steps. The longest chain, mathutil → color → image → (any op) → steps → runner → cli, sets a floor on wall-clock time. Second, every extra agent adds briefing, context loading and merge work. Past some point an extra agent adds more coordination than it removes waiting. This is Amdahl's law applied to agents: the part of the job that cannot run in parallel caps the speedup, and the overhead of each extra worker eats into what remains.

The simulator below uses the starter's numbers: 24 modules in 7 waves. Try 1, 3, 5 and then 20 agents. Look for the point where adding agents stops buying time while cost keeps rising.

At this size, the useful range is small. The widest wave has 14 modules, and most waves have one to three. A team of three to five agents covers the wide wave well and sits idle the rest of the time. You will meet the same curve again in Lesson 19 at 240 modules, where the numbers are bigger and the bend is just as real.

Check yourself

A teammate proposes porting kestrel/core/image.py with three parallel subagents: one for the Image class, one for its pixel accessors, one for the tests. What is the strongest objection?

Pick one

Every option has a reason attached.

Not the strongest

Cost is a real objection, but the 15x figure describes multi-agent systems in Anthropic's research setting. It is an observation about one system, and your ratio will differ. If the split worked, extra cost might be acceptable. The deeper problem is that it would not work well.

Yes

The accessors depend on how the class stores pixels, and the tests depend on both. Each agent would need the others' decisions, which a fresh context does not have. This is the "shared context, many dependencies" case Anthropic flags as a poor fit for multi-agent work. One agent should port image.py.

Not this one

Nothing forbids it. Several subagents in one folder can edit the same file, which is exactly why collisions happen. Lesson 14 deals with that.

Not this one

The default is up to 20 concurrent subagents, set by CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS. Three is well inside it.

Make the call

You have ten minutes before a meeting and want one more module done.

The situation
  1. The task is ops/contrast.py and its tests, nothing else.
  2. Its dependencies are ported and passing.
  3. Your Week 1 recipe already ports one op reliably.

Decide, then see the reasoning.

Right call

One module gives no parallelism. The context fits easily. There is no second job that needs a different role. All four reasons to split are absent, so a team only adds a brief, a handoff and extra tokens.

Not quite

Run down the four reasons. Nothing runs in parallel, the context is small, and there is only one job. A lead plus one subagent is the single-agent recipe with an extra handoff on top.

Lab 06 · In Claude Code ~15 min · est. $0.50–$1.50

Goal. Port three independent ops with three parallel subagents, then compare wall-clock time and cost with your single-agent baseline.

  1. Confirm the three modules are ready. ops/invert, ops/flip and ops/crop should all appear in the list.

    source .venv/bin/activate
python scripts/status.py --next

  2. Open a fresh session. Your Stop hook from Lesson 04 stays active, so the lead cannot finish while any ported module fails its tests. Workers may run in the background, so the hook can fire while one is still writing; the lead should wait for their reports and leave their files alone.

    claude

  3. Note the time on your clock, then type this prompt.

    Use three subagents in parallel, one per module, to port kestrel/ops/invert.py, kestrel/ops/flip.py and kestrel/ops/crop.py, with their tests in tests/ops/, to ts/src/ops/ and ts/test/ops/, following MIGRATION.md.

Each subagent must run scripts/verify.sh on its module until it exits 0, then reply in at most 5 lines:
MODULE, VERIFY (pass or fail), RUNS (how many verify.sh runs), TRAPS (any trap it hit, or none), FILES (files it wrote).

When all three have reported, show me their reports side by side, then run python scripts/status.py.

  4. When the lead finishes, note the time again and check the session cost.

    /usage

  5. Ask the lead a question it should not be able to answer well.

    Which files did the crop subagent read, and what did its first failing test say? Answer only from what you actually received.

  6. Add a row to notes/baseline.md in the Lesson 05 columns: L06 3 subagents as the module, n/a for turns, the total cost from /usage, wall-clock minutes, and interactive; then note the cost per module (total divided by 3) under the table.

What you should see

Three Agent tool calls start together, then three short reports arrive. status.py shows invert, flip and crop ported with passing tests, and ts/src/index.ts gains three export lines, plus probably one explicit re-export, because ops/invert and core/color both export invert. If one worker reports trouble editing index.ts because another worker changed it first, that is the shared-file collision from Part three; Lesson 14 fixes it properly. Your answer to step 5 should be thin: the lead knows what the reports said and little else. Wall-clock time per module should beat your baseline; cost per module probably will not.

Stretch

Change the report format so each worker must also list any line in MIGRATION.md it found unclear. Run it on one more ready op and see whether the lead now learns something it could not learn before. That is a cheap fix for a lossy handoff.

Key takeaway

Split only when you can name the reason: isolation, parallelism, specialization or independent judgement. Every split costs tokens, coordination and lost detail, so design the report format as carefully as the task.
