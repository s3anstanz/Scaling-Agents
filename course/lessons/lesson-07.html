Lesson 07 Week 2 · Small teams ~15 min 3–5 agents

Orchestrator and worker models

The lead plans, routes and judges. The workers execute narrow tasks behind a test gate. Those jobs reward different models, and Claude Code gives you four places to choose one. This lesson shows where each choice wins and where to spend your expensive model.

Part oneTwo jobs that look alike

In Lab 06 every agent ran on the same model. The lead and the three porters were the same kind of Claude doing different jobs. Look at what each one actually did.

The orchestrator (in our sessions, the lead) decided what to split, wrote the briefs, read the reports and decided whether the result was acceptable. Each of those is a judgement call, and a bad one is expensive. A bad split sends every worker in the wrong direction. A careless reading of a report lets a failing module through.

A worker did one narrow thing: port flip.py and its tests, then run scripts/verify.sh until it exits 0. The task was well specified, the context was small, and a script checked the result. If the worker made a mistake, the test caught it and the worker tried again. A worker's mistake costs a few more turns and stays inside one module.

That difference gives you a rule of thumb. Spend model quality where mistakes are expensive and hard to detect. Save it where mistakes are cheap and a check catches them. On Kestrel, that usually means a strong model for the lead and the reviewer, and a cheaper model for bulk porting.

Part twoThe four dials

Claude Code lets you set a model in four places. They stack, and knowing the order saves a lot of confusion.

The main model. This is the lead's model. Set it with --model when you start, /model during a session, or "model" in settings.json. The aliases are opus (Opus 5.5), sonnet (Sonnet 5.5), haiku (Haiku 5.5) and fable (Fable 5.1). There is also opusplan, which uses Opus while the session is planning and Sonnet while it executes. That is the orchestrator-worker idea applied inside one session.

The default worker model. The environment variable CLAUDE_CODE_SUBAGENT_MODEL sets the model for subagents that do not say otherwise. CLAUDE_CODE_SUBAGENT_MODEL=haiku claude --model opus gives you an Opus lead with Haiku workers. Set CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1 as well and every subagent uses that model, whatever else is configured.

The agent file. A subagent defined in .claude/agents/ can name its own model in its frontmatter, for example model: sonnet. The value inherit means "use the main model". You will write these files in Lesson 08.

The single call. When the lead starts a subagent, the Agent tool call itself can carry a model parameter. If you say "use a sonnet subagent for this one", the lead can pass it on that call.

When more than one is set, the highest one in this list wins:

  1. the model parameter on that specific Agent tool call
  2. the subagent's frontmatter model
  3. CLAUDE_CODE_SUBAGENT_MODEL
  4. the main conversation's model

The list runs from most specific to most general. A choice made for one call beats a choice made for one role, which beats a choice made for all workers, which beats the session default.

Effort is a separate dial. It controls how much thinking the model does per step, with levels low, medium, high, xhigh and max. Set it with /effort, --effort, or effort in an agent's frontmatter. A planner on high effort and a porter on medium effort is a reasonable starting point.

Predict first

You start CLAUDE_CODE_SUBAGENT_MODEL=haiku claude --model opus. Your repo has a reviewer agent file with model: opus in its frontmatter. You type: "Use the reviewer agent on ops/flip.py, but run it on sonnet this time." The lead passes model: sonnet on that Agent call. Which model reviews flip? And which model would a plain "use a subagent to port ops/grayscale.py" run on?

The answer

The reviewer runs on Sonnet, because the per-call parameter sits above frontmatter. The plain porting subagent runs on Haiku: it has no frontmatter model and no per-call model, so the environment variable applies. The Opus main model only matters for a subagent when nothing above it is set. If you had also set CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1, both would run on Haiku.

Part threeWhere to spend the expensive model

The useful unit is cost per verified module. A cheap worker that passes on the third try may still cost less than an expensive worker that passes on the first. Or it may not, if its failures are long and wander. You only find out by measuring, which is the lab.

Here is the arithmetic with illustrative numbers, invented for the example. Say a Haiku port attempt costs $0.08 and passes verify.sh on the first try 60% of the time. A Sonnet attempt costs $0.30 and passes first try 90% of the time. If each failure costs roughly one more attempt, Haiku averages about $0.13 per verified module and Sonnet about $0.33. Haiku wins on price. Now suppose half of Haiku's failures are the T1 rounding trap and it "fixes" the test instead of the code. The test gate catches that only if the expected values stay untouched. Your reviewer is what protects the gate, which is why the reviewer is the last place to save money.

The same logic applies upward. The lead sees every report and decides what ships. A lead on a weak model reads "VERIFY: pass" and moves on without noticing that the report lists two test files where there should be one. Lead and reviewer are the leverage points: few calls, high consequence.

RoleModelEffortWhy
Lead (orchestrator)opushighSplits the work and accepts the results. One bad decision is copied into every worker.
Plannerinherit (the lead's model)highA plan is leverage. It is read once and followed many times.
Porter (bulk worker)haiku or sonnetmediumNarrow task, small context, verify.sh checks every result. Pick by cost per verified module.

Same ideas in code. The Agent SDK exposes the same choice: AgentDefinition(description=..., prompt=..., tools=[...], model="sonnet") for each worker and model in the options for the main agent. The labs stay in the CLI.

Check yourself

Your lead runs on Opus. The budget allows Opus in exactly one more role for the next wave of ops. Porters already run on Haiku behind verify.sh. Where does that extra Opus role buy the most?

Pick one

Every option has a reason attached.

Defensible, not best

It might save a few retries on one module. But that porter is already behind a test gate, so its mistakes get caught. Opus there reduces cost of errors that were already contained.

Not this one

That job has no judgement in it. Running a script and formatting a table is exactly where the cheapest model belongs.

Yes

The reviewer is the one place where a mistake is both expensive and invisible: a pass on a bad port. A strong, different model reviewing with a fresh context is what makes cheap porters safe to use.

Not this one

This spends the most and removes the independent check. Better porters still miss things the tests do not cover, and nobody would be looking.

Lab 07 · In Claude Code ~20 min · est. $0.80–$2.50 for both runs

Goal. Port the same three ops twice, once with Haiku workers and once with Sonnet workers under an Opus lead, and compare first-try pass rate and cost.

  1. Save a copy of the barrel file so you can reset between runs.

    source .venv/bin/activate
cp ts/src/index.ts notes/index.ts.before-l07

  2. Start an Opus lead with Haiku as the default worker model.

    CLAUDE_CODE_SUBAGENT_MODEL=haiku claude --model opus

  3. Type this prompt. The last line keeps the lead from overriding the worker model on the call.

    Use three subagents in parallel to port kestrel/ops/grayscale.py, kestrel/ops/threshold.py and kestrel/ops/brightness.py, with their tests, to ts/src/ops/ and ts/test/ops/, following MIGRATION.md.

Each subagent runs scripts/verify.sh on its module until it exits 0 and replies in at most 5 lines:
MODULE, VERIFY (pass or fail), RUNS (verify.sh runs; 1 means it passed first try), TRAPS (any trap hit), FILES.

Do not pass a model parameter on the subagent calls. When all three report, show a table of MODULE, VERIFY and RUNS, then run python scripts/status.py.

  4. Check the cost, write it down along with the RUNS column, then exit.

    /usage

  5. Reset the three modules so the second run starts from the same place.

    rm ts/src/ops/grayscale.ts ts/src/ops/threshold.ts ts/src/ops/brightness.ts
rm ts/test/ops/grayscale.test.ts ts/test/ops/threshold.test.ts ts/test/ops/brightness.test.ts
cp notes/index.ts.before-l07 ts/src/index.ts
python scripts/status.py

  6. Start again with Sonnet workers, run the same prompt from step 3, then /usage.

    CLAUDE_CODE_SUBAGENT_MODEL=sonnet claude --model opus

  7. Add both runs under the table in notes/baseline.md, each with its total cost, wall-clock minutes and first-try passes (how many modules had RUNS = 1). Keep the Sonnet run's files; you will build on them.

What you should see

Both runs end with the three ops ported and passing, because the Stop hook will not let the lead finish otherwise. The difference shows in RUNS and in cost. Haiku workers often need more verify.sh runs and cost less per attempt; Sonnet workers more often pass on the first run. Divide each run's total by 3 to get cost per verified module. Your own numbers decide the porter row in the table. If a cheap worker changed an expected value in a test to make it pass, you have found the reason for Lesson 08's reviewer.

Stretch

Repeat the Haiku run with --effort high on the lead and compare. Then try claude --model opusplan with no subagents at all on one op, and see whether planning on Opus and executing on Sonnet in a single session beats a team for a task this small.

Key takeaway

Put strong models where judgement is concentrated and mistakes are hard to see: the lead and the reviewer. Put cheap models behind a test gate, and choose them by cost per verified module.
