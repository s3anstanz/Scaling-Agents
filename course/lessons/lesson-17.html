Lesson 17 Week 4 · Scale ~16 min 100 agents

Orchestrators of orchestrators

A lead that reads one report per module is fine at 14 modules and lost at 240. Organisations solved this long ago with managers of managers. Agent systems solve it the same way, with a tree that compresses reports on their way up.

Part oneSpan of control

Every time a subagent finishes, its final report lands in the context of whoever started it. You saw this in Lesson 6: only the report comes back, and the parent has to read it. With five workers that is a page of reading. With 240 it is a book.

Put rough numbers on it. Suppose each porter's report runs to about 400 words (an illustrative figure; yours depend on the prompt). Fourteen reports is about 5,600 words, which a lead reads easily. Two hundred and forty reports is about 96,000 words, delivered one at a time while the lead is also trying to plan. Lesson 3 called this context rot. The more a model holds, the less sharply it attends to any single part. The lead does not crash. It just starts missing things: the three failures in ops/ that share a cause, the module that never reported at all.

Managers have the same limit. The usual rule of thumb for span of control, the number of direct reports one person can handle well, is somewhere around five to ten. Past that, a manager stops managing and starts skimming. The fix in organisations is a hierarchy, and it works for agents for the same reason.

Where the limit actually bites. A workflow script can hold 240 result objects in a JavaScript array without any trouble. Arrays do not suffer from context rot. The problem appears at the model steps that have to read results and judge across them: a planner deciding what to do next, a final summariser, a reviewer looking for patterns. Those are the nodes that need a tree beneath them.

Predict first

Your workflow ports all 240 modules of the full Kestrel library, then ends with one opus agent whose prompt contains all 240 result objects and the instruction "summarise for the team". What goes wrong, and what would you change?

The answer

The prompt is enormous before the agent has done any thinking, and the summary comes out generic: "most modules ported, some trap-related failures". The patterns you most need, such as twelve ops/ modules all failing on the same rounding helper, get averaged away. Change the shape. Add one sub-lead per package that reads only its own package's results, re-checks the red ones, and returns five lines. The final agent reads five to ten short summaries and can actually compare them.

Part twoThe shape of a tree

A tree, or hierarchy, is a graph where every node has one parent. In agent terms the root is the lead, the middle layer is sub-leads, and the leaves are workers. Tasks travel down. Summaries travel up. Each node talks only to its parent and its own children, so no node ever has more than a handful of conversations to hold.

A good default is one lead, five to ten sub-leads, and around ten workers per sub-lead. That gives 50 to 100 workers, each node within the span-of-control range. For Kestrel the natural split is by package, because packages are where the code already draws boundaries. The starter's five packages map to five sub-leads.

The tree is lopsided, and that is normal. ops/ is wide; io/ is narrow. In the full library, ops/ holds most of the 240 modules. One ops lead with a hundred-plus workers would just recreate the original problem one level down. So ops/ gets a third layer: an ops lead with about ten group leads (filters, geometry ops, colour ops, and so on), each with about ten porters. Split wherever a node would otherwise have more children than it can read.

There are depth limits to design around. Subagents can spawn subagents up to three layers deep by default (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH). A workflow can call another workflow with workflow(), one level of nesting. A tree for Kestrel-240 fits: the workflow script acts as the root, a sub-lead agent is layer one, a group lead is layer two, and porters are layer three.

Each level reads a bounded amount and sends up less than it read. That ratio is the tree's whole job.

Part threeWhat a summary must keep

Compression throws information away. The design question is which information survives. A sub-lead summary for Kestrel should keep four things and drop the rest.

  1. Counts from the repo. How many modules are green, measured by running scripts/verify.sh. The sub-lead counts exit codes. It does not count its workers' claims.
  2. Every red module, with a one-line cause. "ops/pad: wrap mode returns -1 for x = -1" is useful. "Some issues in pad" is not.
  3. New traps. Anything that should go into MIGRATION.md, so other packages stop rediscovering it.
  4. Cross-package blockers. "analysis/stats is waiting on ops/histogram" belongs to the lead, because only the lead can see both packages.

Everything else stays on disk. Diffs live in the repo, details live in scripts/status.py, and anyone (you or an agent) can drill down when a summary raises a question. This is the blackboard pattern from Lessons 12 and 13 doing its job: the tree moves decisions, and the files hold the facts.

Sub-lead report · ops

10/12 green by verify.sh. Red: ops/blur (rounding at .5 edges, uses Math.round), ops/pad (wrap mode negative modulo). New traps: T1 also hits blur's kernel normalisation; JS % differs for negatives (pad). Blocker for others: none. Suggest adding a roundHalfEven note to MIGRATION.md before analysis starts.

Two failure modes are worth naming. The first is the cheerful summary: a sub-lead reports "all good" because its workers said so. Requiring counts from verify.sh exit codes closes that gap. The second is a game of telephone, where a cause gets reworded at every level until it means nothing. Keep causes as short, concrete phrases with module names in them, and pass them up word for word.

Part fourBuilding the tree in a workflow

There are two ways to build a tree with the tools you have. The first is model-driven sub-leads. The script calls agent() once per package, and the sub-lead decides how to handle its package. The outside is scripted (which packages, in what order) and the inside is model-driven. One catch: workflow agents have no Agent tool, so a sub-lead cannot start porters of its own and ports its package itself. The lab shows this. The second is a nested workflow. A top-level script calls workflow('port-package', ...) for each package, and the inner workflow is fully scripted. That gives you more determinism, at the cost of using your one level of workflow nesting.

The tree and the dependency graph are two different graphs, and you need both. The tree says who reports to whom. The DAG from Lesson 11 says what can run when. ops cannot start until core is green, no matter how the reporting lines are drawn. So the script runs sub-leads in dependency order: core, then ops and io side by side, then analysis and pipeline.

Annotations

Click a marked line to see why it is there.

Line 4 · phases follow the DAG

Packages still have dependencies. core must finish before ops and io, which must finish before analysis and pipeline. The tree says who reports to whom; the phases say what can run when.

Line 14 · the compression contract

The schema caps what travels upward. Counts and red modules are structured fields; the prose is limited to five lines.

Line 22 · model-driven inside

The sub-lead is one workflow agent asked to spawn porters. Workflow agents have no Agent tool, so in practice it ports its package itself, on sonnet. Nested workflow() calls, this lab's stretch, are the way to get real parallel porters per package.

Line 26 · re-verify before reporting

A sub-lead that repeats its workers' claims is a game of telephone. Counting green from exit codes keeps the summary tied to the repo.

Line 35 · parallel siblings

Two sub-leads run at once. Their packages share no files, so they cannot collide.

Line 47 · the lead reads summaries only

The top lead gets five short summaries, not 24 worker reports. At 240 modules that difference is the whole point of the tree.

Line 50 · keep the lead's context clean

If the lead needs detail, a human or a follow-up agent can drill into scripts/status.py. The lead's job is judgment across packages.

Should you add sub-leads to the Lesson 16 workflow that ports the starter's L3 wave?

The situation
  1. The wave has 14 modules, all in ops/ and io/.
  2. The script already collects results in an array and logs green and red.

Decide, then see the reasoning.

Not quite

Each sub-lead is another agent's worth of tokens, and another place where a cause can be reworded. With nobody drowning, the extra layer adds cost and loss without removing a problem.

Right call

Fourteen results held by a script, read by you, is well within anyone's span of control. Add a layer when a model node would have to read more than about ten reports. Kestrel-240 crosses that line; the 14-module wave does not.

What you should see

Three dependency phases followed by a roll-up. The ops sub-lead takes longest, because it has 12 modules and the traps cluster there. The lead's status names the red modules and the shared causes without opening any module. Each sub-lead reports that it could not start subagents and ports its package itself, which works but loses the parallelism. Expect most of the 24 modules green, with stragglers in ops/ or pipeline/.

Stretch

Rebuild the tree with nesting instead. Write port-package.js as a fully scripted workflow (find modules, pipeline port and verify, summarise in five lines), then have a top-level workflow call workflow('port-package', ...) per package in dependency order. Compare determinism and cost with the model-driven version.

Key takeaway

Give every model node a bounded amount to read. A tree of sub-leads, each re-checking against the repo and sending up a few verified lines, lets the top of a 240-module migration think clearly about five things instead of skimming 240.
