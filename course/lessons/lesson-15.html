Lesson 15 Week 3 · Systems ~15 min 10–25 agents

Testing a team

All 24 modules pass their own tests. That tells you each agent did its own job. It does not yet tell you the jobs fit together, and that is the question this lesson answers.

Part oneTwo kinds of check

Every porter in this course has worked against a per-node check: scripts/verify.sh kestrel/<path>.py runs one module's Python tests and its ported TypeScript tests, and passes only if both pass and every Python test name appears in the TypeScript file. It is fast, it is local to one agent's work, and it makes a good loop exit condition. It answers "does this module do what its tests say?"

An end-to-end check asks a different question: does the whole system, run the way a user runs it, produce the right result? For Kestrel, a user runs the CLI on an image file with a pipeline spec such as "gray|threshold:128". The end-to-end check runs that same command on both implementations and compares what comes out.

This is differential testing: you check a new implementation by running it beside a trusted one on the same inputs and comparing outputs. A migration is the ideal case, because you already have the trusted implementation. The Python version is the oracle, the thing whose answer counts as correct by definition. You never have to write down what the right bytes are; Python produces them.

Part twoHow a team passes every test and still fails

A single agent porting all 24 modules would carry one set of assumptions through the whole job. A team does not. Every seam, the place where one module calls another, now has a different agent on each side, each working from its own context. When they assume slightly different things about the data crossing the seam, you get contract drift.

The per-node tests rarely catch it, for three reasons that all apply to Kestrel.

  • Ported tests mirror Python tests. In Python, both sides of every seam were written together in one codebase, so the original authors never needed tests for the seams themselves. The ported test suite inherits that gap.
  • Tests build their own inputs. ts/test/ops/threshold.test.ts constructs a small image by hand. If the image porter and the threshold porter understood pixels differently, each test still passes against its own idea of a pixel.
  • Round-trip tests hide format drift. tests/io/test_ppm.py checks that parsing a formatted image gives the image back. The PPM parser is deliberately lenient about whitespace (trap T5), so a TypeScript writer that lays out whitespace differently from Python still round-trips perfectly.

Small tests make this worse. A test that formats a 2×2 image never exercises behaviour that only appears on wider rows. The samples in samples/ are bigger and messier than unit-test inputs, which is why the end-to-end check runs on them.

Part threeThe differential test

scripts/difftest.py takes one spec. For every .ppm and .pgm file in samples/ (the starter ships tiny.ppm, gradient.ppm, noisy.ppm and checker.pgm), it runs python -m kestrel.cli and, from ts/, npx tsx src/cli.ts with the same input, output path and spec. It compares exit codes and output bytes, prints one row per sample, and ends with a line like 4/4 samples match for spec 'gray|threshold:128'. It exits 0 when everything matches, 1 on any mismatch, and 2 if the TypeScript CLI cannot run yet.

Specs chain steps with |, and a step's arguments follow a colon, separated by commas: crop:0,0,4,4|gray|threshold:128|blur:1. The step names live in the STEPS table in kestrel/pipeline/steps.py.

Predict first

Every module passes verify.sh. You run difftest with three specs: "gray|threshold:128", "invert" and "blur:1". All three report 2/4 samples match, and in each case the mismatches are gradient.ppm and noisy.ppm. Exit codes and output sizes are identical; only the bytes differ. Where do you look first?

The answer

At the path every spec shares. Three unrelated steps fail on the same two files, so the steps are unlikely to be the cause. Both failing files are PPM and wider than tiny.ppm, and checker.pgm is fine. Same size with different bytes suggests a whitespace swap, such as a newline where Python writes a space. The first suspect is the PPM writer in io/ppm, then cli. Looking at which samples fail across several specs often narrows things faster than reading any code.

Part fourAttribution: which node broke it

When the end-to-end check fails, the next question is attribution: which module, and so which agent's work, is responsible. With 24 modules written by many agents, guessing is expensive. Bisect instead. To bisect is to cut the search space in half, or at least into pieces, with each test. You have three axes to cut along.

  1. By step. Run each prefix of the failing spec: gray, then gray|threshold:128. The first prefix that fails names the first bad step. If one step fails alone, check which op module it calls in the STEPS table.
  2. By sample. Ask what the failing samples have in common: format, size, colour or gray, values that land exactly on .5 after a division (trap T1 territory).
  3. By spec. If unrelated specs fail on the same samples, the fault sits in the shared path: parsing, formatting, the runner or the CLI.

Once a module is named, run verify.sh on it. If its own tests pass, you have learned two things at once: where the bug is, and that the module's tests have a gap. Check yourself

The bisector names io/ppm, whose own tests pass. What is the best next step?

Pick one

Every option has a reason attached.

Not this one

The output is wrong on every spec for two of four samples. Nothing about it is random, and calling it flaky teaches everyone to ignore the end-to-end gate.

Yes

Push the check down. The end-to-end failure becomes a per-node test, so the cheap, fast gate catches this bug next time, including in any future re-port. Writing the failing test first also proves you reproduced the right bug. verify.sh only requires every Python test name to appear in the TypeScript file, so an extra TypeScript case is allowed.

Not this one

Byte-identical output is the contract you chose for this migration. Loosening it might be a reasonable decision, but it is a contract change to make on purpose and record in MIGRATION.md. Making it to turn a red test green hides the next real difference as well.

Not this one

A fresh porter reads the same Python and the same tests, so nothing stops it from making the same choice. You pay for a full port and learn nothing. Fix the gap in the tests first.

Part fiveWhere each check lives in a team

Put the two checks at different points in the graph. Each worker runs its per-node gate before it hands off, as your porters already do. The end-to-end gate runs at integration points: after each merge, or after each wave once the CLI exists. It belongs to the orchestrator or the integrator, the agent that sees the whole system, and never to a worker grading its own module. That is the reviewer independence from Lesson 10, applied to a team.

The end-to-end gate is also cheap. A difftest run starts the two CLIs a few times each and burns no model tokens. Compared with what one agent turn costs, you can afford to run a handful of specs after every merge.

Finally, every end-to-end failure should leave a per-node test behind. Over a long migration, that is how the fast gate gets stronger and the slow gate fires less often. At 240 modules in Week 4, you will need the fast gate to carry most of the load.

Lab 15 · In Claude Code ~20 min · est. $1.00–$3.00

Goal. Run the differential end-to-end test across several specs, then use a bisecting subagent to attribute a failure to one module.

  1. Confirm all 24 modules are ported and passing, then save this state so you can return to it.

    source .venv/bin/activate
python scripts/status.py
git add -A && git commit -qm "week 3: all modules ported"

  2. Run the differential test on specs that exercise different steps and traps: T1 in blur, T3 in wrap padding, T2 in resize.

    for spec in "gray|threshold:128" "blur:1" "pad:2,wrap" "resize:5,3" "rotate:3" "equalize" "crop:0,0,2,2|invert"; do
  python scripts/difftest.py "$spec" | tail -1
done

  3. Create the bisecting subagent. It is read-only plus Bash, like your reviewer.

    ---
name: bisector
description: Finds which ported module causes a failing scripts/difftest.py spec. Use when difftest reports a mismatch.
tools: Read, Grep, Glob, Bash
model: sonnet
maxTurns: 30
---
You find the module responsible for an end-to-end mismatch. You never edit files.

1. Run python scripts/difftest.py "<spec>" and note which samples fail.
2. Bisect by step: run each prefix of the spec (split on "|"). The first
   failing prefix names the first bad step.
3. Bisect by spec: run one or two unrelated single-step specs. If they fail
   on the same samples, suspect the shared path: io/ppm, io/pgm,
   pipeline/runner, cli.
4. Map the step to its op module using STEPS in kestrel/pipeline/steps.py.
5. Run scripts/verify.sh on each suspect module, then compare the Python and
   TypeScript code for the function involved.

Report: failing spec and samples, first failing prefix, suspect module and
function, whether its own tests pass, the smallest input that shows the
difference, and the test case that would have caught it.

  4. If every spec matched, plant a bug to find. This headless run changes one TypeScript file so that difftest fails while that module's own verify.sh still passes. It does not tell you which file.

    claude -p "Make one small, realistic change to a single file under ts/src/ so that python scripts/difftest.py reports a mismatch for at least one of these specs: gray|threshold:128, blur:1, invert. scripts/verify.sh for the module you change must still exit 0. Do not edit any test file and do not commit." \
  --model sonnet --max-turns 20 --max-budget-usd 1 \
  --permission-mode acceptEdits \
  --allowedTools "Read,Edit,Glob,Grep,Bash(scripts/*),Bash(./scripts/*),Bash(python scripts/*),Bash(npx vitest*)" \
  < /dev/null > /dev/null

  5. Hand the failure to the bisector.

    claude --model opus
    Run scripts/difftest.py on these specs: "gray|threshold:128", "blur:1", "invert", "pad:2,wrap". For any spec that mismatches, use the bisector agent to find the module responsible. Then show me the test case you would add to that module's TypeScript test so verify.sh would have caught it. Do not edit anything.

  6. Check the bisector's answer against the truth, then restore the ported code.

    git diff --stat
git diff
git checkout -- ts/src
What you should see

Each difftest line ends with something like 4/4 samples match for spec 'blur:1'. If a real mismatch shows up in step 2, you have found genuine contract drift from your own team, which is the best outcome of this lab: bisect it, add the missing test, fix it. Otherwise, after step 4 at least one spec mismatches, the bisector names a module whose own tests pass, and git diff confirms or refutes its answer. Note in notes/baseline.md how many turns and how much the bisection cost compared with porting one module.

Stretch

Add the bisector's suggested test case for real, run scripts/verify.sh on the module with the planted bug still in place to watch it fail, then restore and watch it pass. That is the push-down from Part five, done once by hand.

Key takeaway

Per-node checks prove each agent did its job; only an end-to-end check against the oracle proves the jobs fit together. When the end-to-end check fails, bisect by step, sample and spec to name the module, then turn the failure into a per-node test.
