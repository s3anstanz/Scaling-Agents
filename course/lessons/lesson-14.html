Lesson 14 Week 3 · Systems ~16 min 10–25 agents

Keeping agents out of each other's way

Parallel agents in one folder are parallel writers on one set of files. This lesson gives each agent its own copy of the repo, gives each file one owner, and turns the shared files into something nobody has to fight over.

Part oneWhere agents collide

Lesson 12 left one file open on purpose: ts/src/index.ts, the barrel. A barrel is a file that re-exports other modules so users can import everything from one place. Every Kestrel port adds one line to it, such as export * from "./ops/blur". That makes it a hotspot: a file that every worker needs to change.

Kestrel has a few of these, and so does every real codebase.

  • Index and registry files. The barrel. In bigger projects, route tables, plugin lists and dependency-injection setup.
  • Shared documents. MIGRATION.md Known traps, PLAN.md.
  • Dependency manifests. ts/package.json and its lockfile. One porter that decides to npm install a helper library changes a file all the others build against.
  • Generated output. Anything a build step writes, like compiled files or test caches.

There are two kinds of collision. The first is the lost update from Lesson 12: two agents edit the same file and one edit disappears. The second is quieter and does more damage. Agent A runs its tests while agent B is halfway through editing a shared file. A's tests fail for a reason that has nothing to do with A's module. A is a diligent agent, so it goes looking for the cause, finds B's half-finished edit, and "fixes" it. Now two agents are editing the same lines, each sure the other one broke something.

Part twoIsolation with worktrees

A git worktree is a second working folder attached to the same repository. It has its own checked-out files on its own branch, and it shares the history with the main folder. Edits in one worktree do not appear in another until you merge branches. Claude Code supports worktrees in three ways.

  • claude --worktree <name> (or -w) starts a whole session in .claude/worktrees/<name>/ on a branch called worktree-<name>.
  • isolation: worktree in a subagent's frontmatter gives each run of that subagent its own temporary worktree. If the subagent made no changes, the worktree is removed when it finishes.
  • A .worktreeinclude file lists git-ignored files to copy into new worktrees. Kestrel needs it for ts/node_modules, which git ignores and vitest needs.

With isolation, porter A's test run sees only A's edits. The quiet collision from Part one cannot happen, because B's half-finished file is in another folder.

Isolation does not remove conflicts, though. It moves them. Concurrent collisions become merge conflicts that appear at one known moment, when you merge the branches back. That is a real improvement, since a merge conflict is visible and stops the process, while a lost update is silent. It still leaves you with something to resolve.

Predict first

Four porters work in four worktrees. Each one appends its export line to the end of ts/src/index.ts and commits. You merge the four branches into main one after another, resolving each conflict as it comes. How many merge conflicts do you hit?

The answer

Three. The first merge is clean, because main has not changed. Every later branch added a different line at the same spot, the end of a file that main has now changed in that same spot, so git cannot choose an order and stops. At 14 porters that is 13 conflicts in one file, each one trivial and each one a stop. The fix is to change who writes the file.

Part threeEvery file has one owner

Lesson 12's single-writer rule was about shared documents. Apply it to code too. Ownership means each file in the repo has exactly one agent allowed to change it during a run.

FilesOwnerEveryone else does
ts/src/<path>.ts, ts/test/<path>.test.tsthe porter for that modulereads; reports problems
ts/src/index.tsthe integrator, by scriptnever touches it
MIGRATION.md, PLAN.mdthe orchestratorreports traps and status in the contract
ts/package.json, lockfileyou, the humanasks in notes if it needs a dependency

Ownership for a Kestrel run. Notice that no porter owns any file another porter needs to change.

The hardest case is a bug in someone else's file. Say the resize porter discovers that ts/src/core/mathutil.ts gets floor division wrong for one input. The owner of mathutil finished long ago. The porter must not fix it in its own worktree, because then its branch carries a change to a file it does not own. It reports status: "blocked" with the failing input, and the orchestrator sends a fix to whoever owns mathutil now.

Annotations

Click a marked line. The frontmatter matches the porter.md you wrote in Lesson 8 plus line 8. The body shows only what this lesson adds; your six-line report format (MODULE, VERIFY, RUNS, TRAPS, FILES, NOTES) stays below it.

Line 8 · isolation

Every time this subagent runs, Claude Code creates a temporary worktree for it. Its edits and test runs stay in that folder until you merge its branch. If it changed nothing, the worktree is cleaned up.

Line 11 · ownership, stated positively

The porter learns what it owns before it learns what it must not touch. Agents follow a short explicit list more reliably than a vague "stay in your lane".

Lines 12–13 · the hotspots by name

Name every shared file. The npm install ban protects the lockfile, which is the hotspot people forget until two branches each add a different package.

Lines 14–15 · blocked, with a failing input

Both bad options are tempting to an agent: fix the other module, or copy a corrected floorDiv into its own file. The first breaks ownership; the second hides the bug and leaves two versions of the same function. Blocked plus a failing input sends the problem to the right owner.

Lines 17–18 · commit on green

The branch is the handoff. A commit only after verify.sh exits 0 means every branch you merge has passed its own check, so a failure after merging points at integration.

Part fourThree ways to merge

Ownership leaves one question: who writes the hotspot files, and how? There are three strategies. Prefer them in this order.

StrategyHow it worksKestrel exampleTrade-off
Regenerate from the source of truthA script rebuilds the file from what exists in the reposcripts/gen_barrel.py writes one export line per file in ts/src/Deterministic and free; only works when the file can be derived
One file per writerEach writer appends to its own file; a reader combines themresults/<module>.json from Lesson 12No conflicts possible; someone must combine
Integrator agentOne agent merges branches in order and resolves conflicts with full viewAn integrator merges 14 porter branches and fixes clashes in shared helpersHandles anything; serial, costs tokens, and its judgment can be wrong

Prefer a script over a convention, and a convention over an agent. Use an integrator agent for what is left.

The barrel is the textbook case for regeneration. Its content is fully determined by which TypeScript files exist. A ten-line script produces it, and running the script twice gives the same file. Nobody needs to edit it by hand, so nobody should.

Step through it
  1. The orchestrator starts four porters. Because porter.md says isolation: worktree, each one gets its own folder under .claude/worktrees/ on its own branch.
  2. Each porter edits its module files and appends a line to its own copy of index.ts. Inside the worktrees nothing collides, and every test run sees only that porter's edits.
  3. Porter 1's branch merges first. Main has not changed yet, so the merge is clean.
  4. Porter 2's branch also added a line at the end of index.ts, where main now has porter 1's line. Git stops with a conflict. Porters 3 and 4 will do the same.
  5. Redesign: each porter owns its two files and nothing else. No porter touches index.ts.
  6. Now no two branches change the same file, so all four merge cleanly, in any order.
  7. The integrator runs python scripts/gen_barrel.py, which writes index.ts from the files that exist, then runs the full test suite once.
Check yourself

The resize porter, in its worktree, finds that ts/src/core/mathutil.ts returns the wrong result for floorDiv(-7, 2). Its own tests fail because of it. What should it do?

Pick one

Every option has a reason attached.

Not this one

Now the resize branch changes a file it does not own. If the rotate porter hit the same bug and fixed it differently, you get a merge conflict in mathutil.ts, or worse, two fixes that merge cleanly and disagree.

Not this one

The resize tests pass, the bug in mathutil survives, and Kestrel now has two floor-division functions. The next porter that imports mathutil hits the same bug and makes the same choice.

Yes

The contract's blocked status exists for this. One owner fixes mathutil once, its own tests gain a case for -7, 2, and resize retries against the fixed version. A failing input is what makes the report actionable.

Not this one

This brings back exactly the collision worktrees removed: an unowned edit in the shared folder while other agents are working. It also bypasses mathutil's verify gate.

Goal. Run four worktree-isolated porters, watch the barrel conflict at merge time, then remove it with ownership rules and a regenerated barrel.

  1. Make a throwaway copy with its own git history, so branches and resets cannot touch your real repo. Run this from the folder that contains kestrel-starter. The last line disables your Lesson 4 Stop gate in the copy only, because the copy is deliberately half-broken while you work.

  5. Part B, the fixed design. Create the barrel generator.

    from pathlib import Path

src = Path("ts/src")
lines = [

What you should see

In Part A, four worktrees appear under .claude/worktrees/, all four porters pass, the first merge succeeds, and the second stops on ts/src/index.ts with two different export lines in one conflict hunk. In Part B, all four merges are clean, the generator reports one export per TypeScript file, and the full vitest run and status.py both pass. In your real repo the regenerated barrel may list exports in a new order; the tests should still pass.

Stretch

Make a porter break the rules on purpose: tell one of the four to also "tidy up" ts/src/core/color.ts. Then write a check the integrator runs before merging, using git diff --name-only lab14-start..<branch>, that rejects any branch touching a file outside its module. Ownership you can check beats ownership you only ask for.

Key takeaway

Worktrees turn silent collisions into visible merge conflicts. Ownership and a regenerated barrel remove the conflicts themselves: each worker writes only its own files, and shared files are produced by a script or a single integrator.
