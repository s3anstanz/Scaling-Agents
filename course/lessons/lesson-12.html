Lesson 12 Week 3 · Systems ~15 min 10–25 agents

Handoffs, contracts and shared state

When a worker finishes, a paragraph of prose is all that comes back. At ten agents you need every report in the same shape, and you need a source of truth that does not depend on any agent's word.

Part oneThe lossy handoff

A handoff is the moment work passes from one agent to another. In Claude Code, a subagent's handoff to its parent is its final report and nothing else. The parent never sees the files the subagent read, the commands it ran, or the test it almost skipped. Lesson 6 called this lossy. In Lesson 11 you felt it: the orchestrator read several porter reports, each written in a slightly different style.

Your Week 2 porter already answers in six labelled lines (MODULE, VERIFY, RUNS, TRAPS, FILES, NOTES), which helps a great deal. It is still prose that a model writes and a model reads, and nothing checks it. Here is the kind of report you get without even that much structure, and it shows what goes wrong at scale.

Agent report · porter for ops/resize

Ported resize to TypeScript. The tests look good now. I had to adjust the nearest-neighbour index math a little because of a division difference, and there is one edge case with odd sizes that I simplified. Everything should be working.

Read it as the orchestrator would. Did scripts/verify.sh exit 0, or did the agent run only the TypeScript tests? "Looks good" and "should be working" are beliefs. The division difference is almost certainly the T2 floor-division trap, already in MIGRATION.md, so is this a new trap or an old one? And "simplified an edge case" might mean a test was weakened. With one report you can ask a follow-up question. With fifteen you cannot, and every vague sentence turns into a decision the orchestrator makes on a guess.

The handoff has three problems. Its shape varies, so the reader has to interpret it. It mixes claims with facts, and nothing marks which is which. And it buries details, so the one sentence that matters sits in the middle of a paragraph.

Part twoA contract is a schema

A contract is an agreement on the exact shape of a handoff, fixed before the work starts. For agents, the simplest contract is a JSON schema the final report must satisfy. Headless Claude Code supports this directly. Run claude -p with --output-format json and --json-schema '<schema>', and the JSON it prints includes a structured_output field that matches your schema. The same envelope also carries total_cost_usd and num_turns, so you get cost and effort without asking the agent to report them.

Keep the schema small. Every field should be something the orchestrator will act on. Here is the one this lesson uses for headless porters. It is your six-line report made strict: MODULE becomes module, VERIFY becomes status and tests_passed, TRAPS becomes traps_found, and NOTES stays notes. RUNS and FILES you can measure yourself from the JSON envelope and from git.

Annotations

Click a marked line.

Line 4 · module

The key you join on. It lets you match each result to a row of python scripts/status.py --json without parsing prose. Ask for the Python path, such as kestrel/ops/resize.py, so it matches what verify.sh takes.

Line 5 · status as an enum

Three values, each with its own next action. ported goes to verification. failed goes to retry or a stronger model. blocked means a dependency is wrong or missing, so the fix is somewhere else and a retry would waste money. An enum stops the agent from inventing a fourth state like "mostly done".

Line 6 · tests_passed

A claim, kept separate from status on purpose. A porter can say ported with tests_passed: false when it ran out of turns, which is useful to know. You will still check this field against the repo, because a claim made at minute 4 can be false by minute 9.

Line 7 · traps_found

The porter reports traps here instead of writing them into MIGRATION.md. That keeps the shared file under one writer (Part four). An empty array is a real answer, and the orchestrator can tell it apart from "forgot to mention".

Line 8 · notes

One free-text field for anything the enum cannot hold, such as "weakened the odd-size test". Keep it last and keep it optional in spirit. If you find yourself parsing notes, promote that thing to its own field.

Line 10 · required

Every field is required, so a result with a missing field fails the contract instead of slipping through as half an answer.

Line 11 · no extra fields

Closes the shape. Without it, agents add helpful extras like confidence or summary, and each run's output drifts a little from the last.

The contract is half of the handoff. The other half is the instruction that tells the porter what each field means. "Set tests_passed to true only if scripts/verify.sh exited 0 on your last run" is a definition. "Report whether tests pass" invites the agent to decide what passing means.

Part threeClaims are not facts

Even a perfect contract carries claims. An agent's tests_passed: true means the agent believes the tests passed when it last looked. You need a separate measurement of what is true now.

Kestrel already has one. scripts/status.py builds its table from the repo itself: does the TypeScript file exist, does its test exist, does the test pass. It never reads an agent's report. That makes it a single source of truth, a place whose answer you trust over every other source. It is also derived state: computed fresh from the files each time, so it cannot go stale the way a hand-kept tracker does.

The orchestrator's job after a parallel run is reconciliation: put each claim next to the measurement and look at the disagreements. When they disagree, believe the repo. Then ask why they disagree, because the answer tells you something about your system.

Predict first

Four porters ran in parallel in the same folder. All four return status: "ported" and tests_passed: true. Ten seconds later, status.py shows only three of the four passing. No agent lied. How can this happen?

The answer

Each claim was true at the moment it was made. Then another agent changed something they share. The likeliest culprit in Kestrel is ts/src/index.ts, the barrel file every porter edits: porter B rewrites the file from a stale read and drops porter A's export line, or leaves it half-edited while A's final test run imports it. Engineers call this a time-of-check versus time-of-use gap. It is why reconciliation runs after everyone has finished, against the repo, and never trusts a report on its own.

Part fourShared state: the blackboard and the single writer

So far the porters have never talked to each other. They share information by leaving it in places others can read: the code in ts/src/, the rules in MIGRATION.md, the results in results/. This is the blackboard pattern. Agents read from and write to a shared surface, and a coordinator reads the surface. It is cheap, because nobody sends messages, and it is easy to inspect, because the state is just files you can open.

The blackboard has one serious weakness. Two writers can change the same file at the same time. Agent A reads MIGRATION.md, agent B reads it, A appends a trap and saves, B appends a different trap and saves from its older copy, and A's trap is gone. This is a lost update.

The fix is the single-writer rule: every shared file has exactly one agent allowed to write it. Apply it to Kestrel like this.

Shared thingSingle writerEveryone else
ts/src/ops/resize.ts and its testthe resize porterreads only
MIGRATION.md Known trapsthe orchestratorreport traps in traps_found
results/<module>.jsonthat module's run (one file each)reads only
ts/src/index.ts barrelnobody yetthis lab leaves it open on purpose; Lesson 14 fixes it

One writer per file. Notice the results/ trick: instead of one shared results file, each writer gets its own, so there is nothing to collide on.

Check yourself

Running in parallel, the resize and rotate porters both find the same new trap, one that is not in Known traps yet. What should happen to MIGRATION.md?

Pick one

Every option has a reason attached.

Not this one

Two parallel writers on one file is the lost-update setup. Best case you get the trap twice in slightly different words. Worst case one append erases the other.

Yes

One writer, structured input. The orchestrator sees both reports side by side, which is also the only place where you can notice that two modules hit the same trap. That is a hint it belongs in the rules every future porter reads.

Not this one

Subagents cannot message each other at all; only the final report goes to the parent. Even in agent teams (Lesson 13), negotiating every shared write costs a round of messages to avoid a problem a single writer avoids for free.

Not this one

The next porter that hits the same trap, perhaps on analysis/edges, starts from zero and may get it wrong. Recording traps is how a team gets smarter between waves.

Part fiveParallel headless runs are plain shell

So far your parallel agents were subagents inside one session. You can also run several separate headless sessions at once. Claude Code has no special feature for this. It is ordinary shell: put & after each claude -p command to run it in the background, then wait for all of them, or use xargs -P. Each session has its own context and its own budget. They share only the filesystem.

That makes headless runs a clean fit for contracts. Each run prints one JSON result, which you redirect into its own file. Cap each run with --max-turns and --max-budget-usd. The budget is a client-side estimate and can overshoot by one step, so treat it as a guard rail with a little slack.

Sharing only the filesystem is also the danger. Four sessions in one folder are four writers. They keep to their own module files because you told them to, but every one of them also edits ts/src/index.ts. The lab leaves that collision in place so you can see it. Lesson 14 removes it.

Lab 12 · In your shell, then Claude Code ~20 min · est. $1.00–$3.00

Goal. Run four headless porters in parallel under a JSON contract, collect their results as files, and reconcile those claims against status.py.

  1. Work in a throwaway copy so you can re-port four ops you already have and compare against known-good versions. From the folder that contains kestrel-starter, make the copy and remove four TypeScript ports and their barrel lines. The rm of settings.local.json turns off your Lesson 4 Stop gate in the copy only; otherwise each porter would be sent back to work while the others' modules are still half-done.

    rm -rf kestrel-l12 && cp -r kestrel-starter kestrel-l12 && cd kestrel-l12
rm -f .claude/settings.local.json
for m in threshold resize rotate brightness; do
  rm -f ts/src/ops/$m.ts ts/test/ops/$m.test.ts
  grep -v "/ops/$m\"" ts/src/index.ts > ts/src/index.tmp && mv ts/src/index.tmp ts/src/index.ts
done
python scripts/status.py --next

  2. Launch four porters in the background, one per module, each with the contract, a turn cap and a budget cap. < /dev/null stops a background job from waiting on your terminal.

    SCHEMA='{"type":"object","properties":{"module":{"type":"string"},"status":{"type":"string","enum":["ported","failed","blocked"]},"tests_passed":{"type":"boolean"},"traps_found":{"type":"array","items":{"type":"string"}},"notes":{"type":"string"}},"required":["module","status","tests_passed","traps_found","notes"],"additionalProperties":false}'
mkdir -p results
for m in threshold resize rotate brightness; do
  claude -p "Port kestrel/ops/$m.py and its tests to ts/src/ops/$m.ts and ts/test/ops/$m.test.ts, following MIGRATION.md. Add its export line to ts/src/index.ts. Touch no other files; do not edit MIGRATION.md, list any trap you find in traps_found instead. Run scripts/verify.sh kestrel/ops/$m.py until it passes or you run out of turns. Set module to kestrel/ops/$m.py. Set tests_passed to true only if your last verify.sh run exited 0." \
    --model haiku \
    --output-format json --json-schema "$SCHEMA" \
    --max-turns 25 --max-budget-usd 0.75 \
    --permission-mode acceptEdits \
    --allowedTools "Read,Edit,Write,Glob,Grep,Bash(scripts/*),Bash(./scripts/*),Bash(python scripts/*),Bash(python -m pytest*),Bash(npx vitest*)" \
    < /dev/null > results/$m.json &
done
wait
ls -l results/

  3. Print the claims next to cost and turns. All of it comes from the JSON envelope, none from prose.

    python - <<'EOF'
import glob, json
for f in sorted(glob.glob("results/*.json")):
    r = json.load(open(f))
    s = r.get("structured_output") or {}
    print(s.get("module"), s.get("status"), s.get("tests_passed"),
          r.get("num_turns"), r.get("total_cost_usd"), s.get("traps_found"))
EOF

  4. Check the unprotected shared file. You expect four export lines, one per module.

    grep -nE 'ops/(threshold|resize|rotate|brightness)"' ts/src/index.ts

  5. Open Claude Code in the copy and reconcile. The orchestrator is the single writer for MIGRATION.md.

    claude --model opus
    Reconcile the parallel run. Read every results/*.json (the claim is in structured_output). Run `python scripts/status.py --json` and scripts/verify.sh for each of the four modules. Show me a table: module, claimed status, claimed tests_passed, actual verify result, turns, cost, traps claimed. Flag every row where claim and repo disagree and explain the likely cause. Check ts/src/index.ts for missing or duplicated export lines. Then, as the only writer of MIGRATION.md, append any trap that is genuinely new (deduplicate against the Known traps already listed and against each other). Do not fix any module yet.
What you should see

Four files in results/, each with a structured_output that matches the schema, and real numbers for turns and cost. resize and rotate probably report T2 in traps_found, which the reconcile step should recognise as already known. On some runs the claims and status.py agree completely. On others you find a missing or doubled line in index.ts, or a module that claimed success but fails now. Either outcome teaches the lesson: you only know because you measured. If Haiku failed a module that Sonnet handled in Week 2, rerun just that one with --model sonnet.

Stretch

Rerun the four jobs with xargs -P 4 instead of a loop with &, and give each run its own retry: if structured_output.status is failed, rerun that module once with --model sonnet. Note what the retry cost compared with the first attempt. You will build this retry into a workflow in Week 4.

Key takeaway

Fix the shape of every handoff with a schema, then treat every field in it as a claim and check it against state derived from the repo. Give each shared file exactly one writer, and when you can, give each writer its own file.
