Lesson 04 Week 1 · One agent ~16 min 1 agent

Verification is the exit condition

An agent saying it is finished is a claim. A test passing is evidence. This lesson moves the exit condition out of the prompt and into a Stop hook, so the agent cannot end a session while a ported module is failing.

Part oneThe agent said it was done

Here is a run that goes wrong in a very ordinary way. The agent is porting kestrel/ops/blur.py, a box blur that averages each pixel with its neighbours. The Python rounds each channel's average with round_half_even. The trace is illustrative, and it is the most common failure you will see in single-agent ports.

thinkPort blur.py. Read the source and the tests.
toolRead: kestrel/ops/blur.py
toolRead: tests/ops/test_blur.py
toolWrite: ts/src/ops/blur.ts (channel = Math.round(sum / count))
toolWrite: ts/test/ops/blur.test.ts
toolBash: npx vitest run test/ops/blur.test.ts -t "radius 0"
result2 passed
stopPorted box_blur and its tests. Tests pass.

Then you run the real check.

youscripts/verify.sh kestrel/ops/blur.py
resultexit 1 · averages halves to even: expected [2, 2, 2], received [3, 3, 3]

Two things went wrong, and they compound. The agent used Math.round, which rounds 2.5 up to 3, where Kestrel must produce 2. That is trap T1. Then it ran a narrow slice of the tests, the radius-0 cases where no averaging happens, and reported success. Its report was sincere. From inside its context, the evidence said done.

Lesson 02 put the success check into the prompt. That helps, but the agent still decides whether it ran the check, which check, and whether the result counts. A prompt instruction is a request. To make the exit condition reliable, it has to be enforced by something outside the model.

Part twoWhat makes a good check

In a migration the tests are the oracle: the independent source of truth about correct behaviour. The Python tests were written before any agent arrived, they pass on the Python code, and the TypeScript port must pass the same cases. A check worth using as an exit condition has four properties, and scripts/verify.sh has all four.

  • Mechanical. It returns an exit code. No judgement, no reading of prose.
  • Complete for its scope. It runs all of a module's tests on both sides, not the slice the agent chose.
  • Fast. Seconds per module, so running it on every stop attempt is affordable.
  • Independent of the agent's opinion. The agent cannot argue with it.

One weakness remains, and you should know it before you rely on any test-based gate. The agent also ports the tests. If it weakens a TypeScript test, say by changing an expected [2, 2, 2] to [3, 3, 3] to match its output, the TypeScript side passes against a corrupted oracle. verify.sh blocks the crudest version of this: it fails unless the TypeScript test file contains every Python test name, so cases cannot simply disappear. It cannot tell whether an expected value was changed. Read the test diffs of early ports. In Week 2 you will give this job to a reviewer agent that never edits code.

Part threeThe Stop hook

A hook is a command Claude Code runs at a fixed point in its lifecycle. A Stop hook runs when Claude tries to finish its reply. It gets a small JSON object on stdin, and its exit decides what happens next.

  • Exit 0: Claude is allowed to stop.
  • Exit 2: Claude is sent back to work, and whatever the hook wrote to stderr is given to it as the reason. Printing {"decision":"block","reason":"..."} to stdout does the same thing in JSON form.

That turns the loop's success check from an instruction into a gate. When the blur agent above tries to stop, the hook sees that blur's TypeScript tests fail and returns that as the reason. The agent never gets to write its confident report; it gets the test output instead, and the loop continues.

Any gate that can say no can say no forever, so two safeguards matter.

stop_hook_active. The hook's input includes this field. It is true when Claude is already continuing because a Stop hook blocked it earlier. The usual pattern, and the one you will write, is to exit 0 immediately when it is true. That gives the agent exactly one push-back per attempt to finish: it hears the failure, works on it, and its next stop goes through. It cannot get trapped in a block-continue cycle on a task it cannot finish.

The continuation cap. Claude Code also caps consecutive stop-hook continuations at 8 (CLAUDE_CODE_STOP_HOOK_BLOCK_CAP). The count resets whenever Claude calls a tool, so the cap is a backstop for a hook that blocks without the agent doing anything in between. Treat it as a seatbelt.

The trade-off is real. A gate that ignores stop_hook_active keeps sending the agent back for as long as the tests fail and the agent keeps working, which is stricter and riskier: on an impossible task, only your turn and budget caps end it. The one-push-back gate is the safer default for interactive sessions. You will see stricter, counted versions of this loop in Weeks 2 and 4, where a script tracks rounds and escalates instead of looping.

Predict first

The gate blocks the blur agent with the rounding failure. The agent switches to roundHalfEven, but makes a new mistake in the edge handling, and tries to stop again. What does the gate do on this second attempt?

The answer

It lets the agent stop without running anything. The second stop arrives with stop_hook_active set to true, and the gate exits 0 at once. The agent's report will often say it fixed the failure, which is true of the rounding, and say nothing about the edge bug. This is why you still run verify.sh yourself after an interactive session, and why Lesson 05's recipe keeps the success check in the prompt as well as in the hook. The hook guarantees the agent hears about a failure once; the prompt asks it to keep checking.

Annotations

Click a marked line.

Line 6 · find the repo root

Paths are resolved from the script's own location, so the gate works whatever directory the hook happens to run in.

Line 10 · the hook's input

Claude Code sends a JSON object on stdin. This gate needs one field from it.

Lines 11–12 · one push-back per stop

If Claude is already continuing because of a Stop hook, let it stop. This is what prevents an endless block-continue cycle on a task the agent cannot finish.

Line 13 · status derived from the repo

status.py --json returns one object per module, built from the files on disk, and runs vitest once over every TypeScript test file present. The agent's report never decides what gets checked, and earlier modules are re-tested on every stop.

Lines 15–17 · a blind gate blocks

If the status script itself fails, the gate cannot see, so it says no and passes on the error. Because of line 11, that still costs at most one push-back.

Line 20 · judge only ported modules

A module counts as ported when its ts/src file exists. Unported modules are future work, not failures.

Line 24 · only a clear pass is a pass

ts_tests_pass can be true, false, "unknown" (vitest could not report) or null. Anything other than an unambiguous true blocks.

Line 28 · a short, actionable reason

Whatever the gate prints lands in the agent's context, so it names the module and the exact command to run, and nothing else. A full test log would spend the window on noise, which is Lesson 03's point. verify.sh gives the agent the failing assertion when it needs it.

Lines 30–31 · stderr is the message

With exit code 2, stderr is what Claude reads as the reason it was sent back. Write it as an instruction to the agent.

Line 32 · exit 2 blocks the stop

Exit 2 sends Claude back to work. Exit 0 on the next line lets it finish.

Check yourself

A teammate copies your gate but deletes the stop_hook_active check, reasoning that a stricter gate is a better gate. What is the most likely bad outcome?

Pick one

Every option has a reason attached.

Not this one

The hook is still valid. The settings shape and the exit-code contract are unchanged; only the decision logic is different.

Yes

Each block sends the agent back, it calls tools trying to fix things, and the tool calls reset the continuation counter. On something it truly cannot fix, such as a module whose dependency is not ported, it keeps going. That is a never-stopping loop from Lesson 02, built on purpose. Strict gates need a round counter and an escalation path, which Week 2 adds.

Not this one

The cap of 8 counts consecutive continuations and resets when Claude calls a tool. An agent actively trying fixes will keep resetting it, so the cap rarely ends this kind of loop.

Not this one

Strictness without a way out turns every hard failure into a long, expensive session. The useful kind of strict is a gate plus a limit plus a report of why it stopped.

Lab 04 · In Claude Code ~20 min · est. $0.30–$1.50

Goal. Write the stop gate, prove it blocks on a failing module, then port geometry.py with the gate switched on.

  1. From the repo root, activate the environment and confirm the tree is clean.

    source .venv/bin/activate
git status --short

  2. Create the gate.

    import json
import subprocess
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent


def main():
    event = json.load(sys.stdin)
    if event.get("stop_hook_active"):
        sys.exit(0)
    status = subprocess.run([sys.executable, "scripts/status.py", "--json"],
                            cwd=ROOT, capture_output=True, text=True)
    if status.returncode != 0:
        print("Stop gate: scripts/status.py failed.\n" + status.stderr[-800:], file=sys.stderr)
        sys.exit(2)
    failures = []
    for row in json.loads(status.stdout):
        if not row["ported"]:
            continue
        if not row["ts_test_present"]:
            problem = "ported, but its TS test file is missing"
        elif row["ts_tests_pass"] is not True:
            problem = f"TS tests not passing ({row['ts_tests_pass']})"
        else:
            continue
        failures.append(f"{row['module']}: {problem}. Check with scripts/verify.sh {row['py']}")
    if failures:
        print("Not done. Fix these ported modules before finishing:", file=sys.stderr)
        print("\n".join(failures), file=sys.stderr)
        sys.exit(2)
    sys.exit(0)


if __name__ == "__main__":
    main()

  3. Test it by hand, before any agent depends on it. Both lines should print exit=0: errors, mathutil and color all pass.

    echo '{"stop_hook_active": false}' | python scripts/stop_gate.py; echo "exit=$?"
echo '{"stop_hook_active": true}' | python scripts/stop_gate.py; echo "exit=$?"

  4. Break a module on purpose by appending a test that can never pass, and run the gate again. It should print a line for core/color and exit=2.

    printf '\nimport { test as gateCheck, expect as gateExpect } from "vitest";\ngateCheck("gate check", () => gateExpect(1).toBe(2));\n' >> ts/test/core/color.test.ts
echo '{"stop_hook_active": false}' | python scripts/stop_gate.py; echo "exit=$?"

  5. Register the hook. If .claude/settings.local.json already exists, add the hooks key to it instead of replacing the file.

    {
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command", "command": "python scripts/stop_gate.py" } ] }
    ]
  }
}

  6. Start a new session from this shell, so it picks up the new settings and the active environment.

    claude --model sonnet

  7. Ask for something trivial and watch what happens when it tries to stop.

    Reply with the single word ready.

  8. The gate blocks, and Claude gets the failing test as its reason to continue. Let it investigate. If it asks what to do, tell it this.

    The "gate check" test at the end of ts/test/core/color.test.ts was added on purpose to test the stop hook. Remove it and its import line, run scripts/verify.sh kestrel/core/color.py, then stop.

  9. Exit with /exit. Confirm the test file is back to its committed state; if anything remains, restore it.

    git diff --stat ts/
git checkout -- ts/test/core/color.test.ts

  10. Now port geometry in a fresh, timed session. The prompt removes the agent's own check on purpose, so the gate is the only thing standing between a wrong port and a finished session.

    start=$SECONDS
claude --model sonnet
echo "geometry $((SECONDS - start))" >> notes/runs/seconds.txt
    Port kestrel/core/geometry.py to ts/src/core/geometry.ts and its tests from tests/core/test_geometry.py to ts/test/core/geometry.test.ts, following MIGRATION.md including its Known traps, and add the module's export line to ts/src/index.ts. Do not run any tests or scripts yourself: write the files, then stop.

  11. Before exiting that session, note its cost. Write the dollar figure down; Lesson 05 puts it in the baseline.

    /usage

  12. After /exit, check the work yourself and checkpoint.

    scripts/verify.sh kestrel/core/geometry.py; echo "exit=$?"
git add -A && git commit -qm "lab 04: stop gate, port geometry"
What you should see

In step 7, Claude replies ready, then the session shows your gate's stderr: core/color is not passing, with the verify.sh command to run. Claude runs it, finds the failing gate check test, and, with or without your nudge, removes it. For geometry, one of two things happens. If the port was right first time (likely, since Known traps now warns about floor_div), the gate passes silently and the session ends. If not, you see the gate send it back naming core/geometry, and the agent runs verify.sh and fixes it, even though you told it not to run tests. Either way, step 12 should print exit=0.

Stretch

Make the gate say more: for each failing module, run scripts/verify.sh on it and append the last five lines of its output to the message, so the agent sees the failing assertion without another tool call. Test it by hand as in step 4, restore the test file, and think about the trade: fewer turns, but more text in the context on every block.

Key takeaway

Done should be a command that passes, checked by something other than the agent. A Stop hook makes that mechanical; stop_hook_active and the continuation cap keep the gate from becoming a trap.
