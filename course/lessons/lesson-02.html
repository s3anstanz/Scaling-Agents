Lesson 02 Week 1 · One agent ~15 min 1 agent

Designing the loop

A loop is defined by how it ends. This lesson covers the four stop conditions every agent run needs, what happens inside each iteration, and the three ways a loop goes wrong when a stop condition is missing.

Part oneFour ways to stop

In Lesson 01 the agent stopped because it decided to. That is fine when it decides well. Loop engineering is the practice of designing the loop deliberately: what ends it, what happens on each pass, and where the checks sit. It starts with stop conditions, because a loop without good exits will eventually either quit too soon or never quit.

There are four exits worth designing for. Only one of them means the work is good. The other three are guard rails that end a run that is not getting there.

Stop conditionOn KestrelEnforced byWhat it catches
Success checkscripts/verify.sh kestrel/core/mathutil.py exits 0The agent, because the prompt says so (made mechanical in Lesson 04)The normal, happy ending. The only exit that tells you the port is right.
Turn cap--max-turns 20Claude CodeRuns that never converge, such as an agent porting half the library to satisfy one import.
Budget cap--max-budget-usd 1Claude CodeRuns that converge too slowly or read far too much. The cap is a client-side estimate and can overshoot by one step.
No progressThe same test fails the same way twice in a rowThe agent, because the prompt says so (scripted in Weeks 2 and 4)Thrashing: edits that undo each other while the turn counter climbs.

The cap values are the ones used in this lesson's lab. Pick yours from the size of the task.

Notice the split in the third column. Two exits are enforced by the harness and cannot be argued with. Two depend on the agent following instructions. A well-designed loop moves the important ones into machinery over time, which is the arc of this week: the success check becomes a Stop hook in Lesson 04, and no-progress detection becomes code in later weeks.

Part twoWhat happens in one iteration

It helps to know exactly what the harness does on each pass, because every cost and every failure happens somewhere in this sequence. In headless mode (claude -p), one iteration looks like this.

  1. Call the model with everything so far: system prompt, CLAUDE.md, your prompt, and every earlier tool request and result.
  2. Read the reply. If it contains no tool request, the run is over and the reply becomes the result.
  3. Check permissions. Is the requested tool allowed? In headless mode there is nobody to ask, so a tool that is not allowed is refused and the refusal goes back to the model as a result.
  4. Run the tool and capture its output.
  5. Append the request and the output to the conversation.
  6. Check the caps. Turn count and estimated spend. If either is exceeded, the run ends here.

Step 1 is where the money goes, and it tends to get more expensive as the run goes on, because each call carries the whole conversation so far. Twenty turns are not twenty equal steps. A run that reads every file in kestrel/ early pays for that reading on every later call. Lesson 03 is about that problem.

Step 3 is where headless runs most often go quietly wrong. If Bash(scripts/*) is not allowed, the agent cannot run verify.sh. It may then report success based on reading its own code, which is the first failure mode below. That is why every headless command in this course passes --allowedTools explicitly.

Step through it
  1. Iteration 1 begins. The agent reads kestrel/core/mathutil.py, tests/core/test_mathutil.py and MIGRATION.md.
  2. It writes ts/src/core/mathutil.ts. floor_div becomes Math.trunc(a / b), which is correct for every positive input it thinks of.
  3. verify.sh exits 1. The TypeScript test for floor_div(-7, 2) expects -4 and gets -3. Python's // floors toward negative infinity; Math.trunc cuts toward zero. This is trap T2.
  4. Before going around again, every exit is checked. Tests pass? No. Turn 7 of 20, about $0.15 of $1 (illustrative numbers): under both caps. The failure is new, so there is progress. Keep going.
  5. Iteration 2. The agent rereads the floor_div docstring, switches to Math.floor(a / b) and keeps the divide-by-zero error the Python raises.
  6. verify.sh exits 0. The success check fires, so the agent stops and writes its report. Two passes of the outer loop, around a dozen tool calls.

Part threeThree ways a loop fails

Each missing stop condition produces a recognisable failure. Once you can name them, you will see them in transcripts everywhere.

Stopping early. The agent reports success because the work looks done. It wrote mathutil.ts, the code reads well, and it says so. Or it ran the Python tests, saw them pass, and took that as the answer, though the Python side was never in doubt. The cause is a missing or vague success check. A prompt that says port mathutil invites this. A prompt that says run scripts/verify.sh kestrel/core/mathutil.py until it exits 0 makes it much less likely, and Lesson 04 makes it close to impossible.

Never stopping. The agent keeps working on something that cannot be finished inside the task. A common Kestrel version: you ask for geometry.py before mathutil is ported. The TypeScript import fails, so the agent ports mathutil too, then notices errors is missing and ports that, and the scope keeps widening. Each step is reasonable. The run as a whole is not what you asked for. The turn cap and budget cap end it; the real fix is giving tasks in dependency order, which is what scripts/deps.py --layers is for.

Thrashing. The agent alternates between fixes. It changes floorDiv to Math.floor, a different test fails, it changes back to Math.trunc, the first test fails again. Every iteration looks like work. No-progress detection catches it: if the same failure comes back, stop and report it rather than trying again. That report is worth more than another ten turns, because it tells a human (or, later, a reviewer agent) exactly where the agent got stuck.

Predict first

You run a headless port with --max-turns 20. The agent needs 25 turns to finish. When the run ends at turn 20, what state is the repo in?

The answer

Exactly as the agent left it at turn 20. A cap ends the loop; it does not undo anything. You may have a half-edited mathutil.ts, a test file that does not compile, and a new line in ts/src/index.ts pointing at it. The JSON output tells you the run ended on a limit rather than a success (look at is_error and subtype), but the files are your problem. This is why the labs commit a git checkpoint before each run, and why, from Week 3 on, agents work in isolated copies of the repo.

Part fourWriting the loop into the command

For one agent, you design the loop in two places: the prompt, which carries the success check and the no-progress rule, and the command line, which carries the caps. Here is the shape of the command you will run in the lab.

headless port of mathutilClick a marked line
  7. 7
      > notes/runs/mathutil.json
Annotations

Click a marked line.

Line 1 · the prompt carries two exits

-p runs one task with no interactive session. The prompt names the success check as a command with an exit code, and the no-progress rule as a concrete trigger. Both depend on the model following them, which is why the caps below exist.

Line 2 · fix the model

Pinning the model makes runs comparable. The baseline you build this week uses sonnet throughout, so Week 2 can compare cheaper and pricier workers against it.

Line 3 · the harness exits

The turn cap and budget cap are enforced by Claude Code, whatever the model thinks. The budget is a client-side estimate and can run over by one step, so treat it as a ceiling with a small margin.

Line 4 · a machine-readable result

JSON output includes num_turns and total_cost_usd, plus fields saying whether the run ended in an error. This is how you measure a loop instead of guessing.

Line 5 · edits without prompts

In headless mode nobody can approve an edit. acceptEdits lets file edits through so the loop can actually change code.

Line 6 · the tools the loop needs

Reading, writing, and the exact shell commands the success check uses. Without Bash(scripts/*) the agent could not run verify.sh, and the success check would silently disappear.

Check yourself

An agent porting mathutil keeps switching floorDiv between Math.trunc and Math.floor, failing a different test each time. Which stop condition ends this run soonest and leaves you the most useful result?

Pick one

Every option has a reason attached.

Not this one

The success check never fires here, because the tests never all pass. That is the whole problem with thrashing: the good exit is out of reach.

Not this one

The turn cap will end it, eventually, after spending every remaining turn. You also get no explanation, only a run that hit its limit with the code in whichever state the last flip left it.

Not this one

Same as the turn cap, measured in dollars. It is a backstop for runaway cost. It says nothing about why the agent was stuck.

Yes

The first time the same failure comes back, the agent stops and reports which test fails and what it tried. That is cheaper than the caps and far more useful: it points straight at the disagreement (here, two tests that need different rounding behaviour), which a human or a reviewer can resolve.

Lab 02 · In Claude Code ~15 min · est. $0.30–$1.50

Goal. Port the two wave-L0 modules, errors and mathutil, with bounded headless runs, and read the loop's numbers from the JSON.

  1. From the kestrel-starter root, activate the environment and make a folder for run records.

    source .venv/bin/activate
mkdir -p notes/runs

  2. Create a small script that prints the loop numbers from any run file. You will reuse it all week.

    import json
import sys

for path in sys.argv[1:]:
    with open(path) as f:
        run = json.load(f)
    print(path)
    for key in ("subtype", "is_error", "num_turns", "total_cost_usd"):
        print(f"  {key}: {run.get(key)}")

  3. Port errors, the smallest module, timing the run. $SECONDS works in bash and zsh.

    start=$SECONDS
claude -p "Port kestrel/core/errors.py to TypeScript at ts/src/core/errors.ts, following MIGRATION.md. Port its tests from tests/core/test_errors.py to ts/test/core/errors.test.ts, and add the module's export line to ts/src/index.ts. Run scripts/verify.sh kestrel/core/errors.py and keep fixing until it exits 0. If the same test fails the same way twice in a row, stop and report the failure instead. Finish with three lines: what you ported, how many verify runs it took, and any Python-vs-JavaScript difference you had to handle." \
  --model sonnet \
  --max-turns 20 --max-budget-usd 1 \
  --output-format json \
  --permission-mode acceptEdits \
  --allowedTools "Read,Edit,Write,Glob,Grep,Bash(scripts/*),Bash(python -m pytest*),Bash(npx vitest*)" \
  > notes/runs/errors.json
echo "errors $((SECONDS - start))" >> notes/runs/seconds.txt
python scripts/runinfo.py notes/runs/errors.json

  4. Now mathutil. It holds the two helpers that exist because of traps: round_half_even (T1) and floor_div (T2).

    start=$SECONDS
claude -p "Port kestrel/core/mathutil.py to TypeScript at ts/src/core/mathutil.ts, following MIGRATION.md. Port its tests from tests/core/test_mathutil.py to ts/test/core/mathutil.test.ts, and add the module's export line to ts/src/index.ts. Run scripts/verify.sh kestrel/core/mathutil.py and keep fixing until it exits 0. If the same test fails the same way twice in a row, stop and report the failure instead. Finish with three lines: what you ported, how many verify runs it took, and any Python-vs-JavaScript difference you had to handle." \
  --model sonnet \
  --max-turns 20 --max-budget-usd 1 \
  --output-format json \
  --permission-mode acceptEdits \
  --allowedTools "Read,Edit,Write,Glob,Grep,Bash(scripts/*),Bash(python -m pytest*),Bash(npx vitest*)" \
  > notes/runs/mathutil.json
echo "mathutil $((SECONDS - start))" >> notes/runs/seconds.txt
python scripts/runinfo.py notes/runs/mathutil.json

  5. Do not trust the report; run the exit condition yourself, then read the agent's final message and look at how it handled the two helpers.

    scripts/verify.sh kestrel/core/errors.py; echo "exit=$?"
scripts/verify.sh kestrel/core/mathutil.py; echo "exit=$?"
grep -n -i -E -A4 "floor_?div|round_?half_?even" ts/src/core/mathutil.ts
git diff MIGRATION.md

  6. Checkpoint the work so later labs can reset safely.

    git add -A && git commit -qm "lab 02: port errors and mathutil"
python scripts/status.py
What you should see

Two run records with a small num_turns for errors and a larger one for mathutil, each well under $1. Both verify.sh calls print exit=0. In the mathutil report, look for T2: a first attempt with Math.trunc that failed on negative inputs, or a note that Math.floor was needed. You may also see T1, since Math.round(2.5) is 3 while round_half_even(2.5) must be 2; a naive port fails the round_half_even, floor_div and mean_int tests. If the agent got both right on the first try, it probably read the docstrings carefully; the test still checked it. CLAUDE.md tells agents to add a bullet to Known traps in MIGRATION.md when they find a difference, so git diff MIGRATION.md may already show one. Lab 03 tidies those entries up. status.py now shows two ported modules.

Stretch

See a cap fire. Remove the mathutil port with git rm -q ts/src/core/mathutil.ts ts/test/core/mathutil.test.ts, rerun step 4 with --max-turns 3 writing to notes/runs/cap-test.json (and skip the seconds.txt line), inspect it with runinfo.py, then restore everything with git reset -q --hard.

Key takeaway

Give every run one good exit (a command that passes) and three guard rails (turns, budget, no progress). Caps end a run; they do not clean up after it, so checkpoint before you start.
