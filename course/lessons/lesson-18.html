Lesson 18 Week 4 · Scale ~17 min 100 agents

Loops at scale

With one agent, a failure is an event. With a hundred, failure is the weather. This lesson takes the loop engineering from Week 1 and rebuilds it for a fleet: retries that learn, runs that are safe to repeat, a breaker that stops a doomed wave, and budgets that hold.

Part oneSomething is always failing

Suppose each agent run has a 3% chance of failing for reasons that have nothing to do with your code: a timeout, a confused turn, a tool call that went sideways. That number is illustrative, but the arithmetic is not. Across 100 agents you should expect about three such failures per run, and the chance that all 100 succeed is 0.97 to the power of 100, which is under 5%. At scale, "everything worked" is the rare case. Your design has to treat failure as normal traffic.

Not all failures are alike, and each kind wants a different response. Getting this wrong is expensive in both directions. Retrying a deterministic failure burns money. Giving up on a transient one wastes the work around it.

KindKestrel exampleSignalResponse
TransientAn agent stops early or returns nothingagent() returns null; no clear errorRetry once, as is
Deterministicops/blur uses Math.round and fails T1Same assertion fails againRetry with the error in the prompt, then escalate the model or stop
Upstreamcore/image.ts is broken, so every op failsMany modules fail at once, all pointing at the same dependencyStop the wave. Fix the dependency. Rerun
RunawayAn agent rewrites blur.ts for 60 turnsTurns and cost climb with no new passing testsTurn caps, budgets, and a kill switch

Classify first, respond second. Most of this lesson is about telling the third row apart from the second.

Part twoRetries with a cap, and runs that are safe to repeat

A retry is an experiment. Running the same prompt against the same failure is the same experiment twice, and it usually gets the same answer. So every retry carries new information: the exact failing line from scripts/verify.sh, pasted into the prompt. That turns a blind repeat into the evaluator-optimizer loop from Lesson 10, where the verify script plays evaluator.

Retries also need a cap. Two extra attempts is a sensible default for porting. If a module has failed three times with the error in front of it, something is wrong that a cheap worker will not fix on attempt four. Escalate it to a stronger model, or report it red and let a human look.

The second half of recovery is idempotency. An operation is idempotent when doing it twice has the same effect as doing it once. For a Kestrel porter, that means three habits. It checks scripts/status.py before touching anything and skips modules that are already green. It writes only its own module's files, so a second run overwrites rather than duplicates. And it never appends to shared files, because an append done twice is two appends. With those habits in place, the universal recovery for any interrupted run becomes "run it again". Pressing x in /workflows stops being scary.

Predict first

A workflow is porting the 14 modules of wave L3. Nine are green when your laptop sleeps and the run dies. You start it again. What happens if the porters are idempotent? What happens if they are not, and each one also appends its export line to ts/src/index.ts?

The answer

Idempotent: nine agents check status, return skipped within a turn or two, and the five unfinished modules get ported. You pay a little for the checks and nothing for rework. Not idempotent: all 14 port again from scratch, which roughly doubles the cost of the wave. Worse, the nine finished modules now have two identical export lines each in the barrel, so the TypeScript build breaks on code that was green an hour ago. This is why Lesson 14 moved barrel edits to a single integrator.

Part threeCircuit breakers

A circuit breaker in your house cuts the power when too much current flows, before the wiring melts. The software version does the same thing for failures. It watches the failure rate, and when the rate crosses a threshold it stops sending work into a system that is clearly broken.

Kestrel's dependency graph makes this essential. Every module in wave L3 (twelve ops and two io readers) imports core/image. If image.ts is broken, all 14 will fail, and each porter will spend its full turn budget discovering that. Worse, a well-meaning porter may try to "fix" image.ts itself. Fourteen agents patching one shared file in fourteen different ways is how a single bug becomes a merge disaster.

The defence has three parts. First, send a small canary batch: three modules go ahead of the rest. Second, teach porters a blocked status. A porter that sees a broken dependency stops and reports it, and it never edits outside its module. Third, the breaker: if more than 30% of the canaries come back failed or blocked, the rest of the wave never starts. The 30% threshold is illustrative. Start there, and tune it once you know your normal failure rate.

Step through it
  1. A scout agent runs scripts/status.py --next and gets the 14 modules of wave L3. Today, unknown to anyone, image.ts has a broken pixel accessor.
  2. Three canaries start: blur, crop, flip. The other eleven wait. Each canary first checks status, so a rerun would skip anything already green.
  3. blur fails verify.sh and does not spot the cause. It gets a retry with the failing line pasted in, then a second. Still red after the cap of two.
  4. crop and flip trace their failures into image.ts. Following the rules, they return blocked without editing it. Blocked modules get no retries.
  5. The breaker counts three red out of three. 100% is far above the 30% threshold.
  6. The wave stops. Eleven porters never start. The report names the shared cause, image.ts. You fix it and rerun, and idempotency makes the rerun safe.
  7. On a healthy day, zero or one canary is red, which is under the threshold, and the other eleven start. The canary cost you a few minutes of wall-clock and nothing else.

Annotations

Click a marked line to see why it is there.

Line 7 · breaker threshold

Stop the wave if more than 30% of the canaries fail or are blocked. The number is illustrative. Tune it to your own failure rate once you have one.

Line 8 · canary size

Three modules go first. If the shared dependency is broken, you find out after three agents, not fourteen.

Line 9 · retry cap

At most two extra attempts per module. A third retry with the same information rarely fixes what two did not.

Line 21 · blocked is not failed

A porter that finds a broken dependency stops and says so. It must not patch image.ts on its own, because 14 agents patching the same file in 14 ways is worse than the original failure.

Line 24 · idempotency

Every agent checks scripts/status.py before touching anything. Running the workflow twice is safe, so rerun it becomes the standard recovery.

Line 31 · retry only on failed

The loop retries failed and never blocked. Retrying a module whose dependency is broken burns money and teaches nothing.

Line 32 · retry with new information

Each retry gets the previous error in its prompt. A retry without new information is the same experiment run twice.

Line 45 · the breaker

Count the red canaries. Above the threshold, the rest of the wave never starts.

Line 46 · budget guard

budget.remaining() tells the script how much of the run's budget is left. Below 20% after the canaries, it stops cleanly instead of running out halfway through a wave.

Line 55 · reconcile with the repo

The final word comes from scripts/status.py. Any mismatch with an agent's report is logged, because an agent that reports green while the repo shows red points to a bug in your process.

Check yourself

All three canaries come back red. Two say blocked with the error "img.getPixel is not a function" from ts/src/core/image.ts. What should the workflow do next?

Pick one

Every option has a reason attached.

Not this one

The error is upstream. No amount of retrying crop fixes image.ts, and the porters are forbidden from editing it. Retries here buy six more failures.

Not this one

Three out of three, with the same named dependency, is strong evidence. Starting eleven more agents to confirm it is the exact waste the canary exists to prevent.

Yes

The breaker's job is to stop correlated failure early and hand over a clear cause. Fixing a dependency that every op relies on is a decision worth a human glance, and the idempotent rerun picks up from there.

Not this one

Tempting, and sometimes right in a mature system. Here it lets an agent change a module that was green yesterday with nobody looking, mid-wave, based on one error message. A separate, deliberate run to repair image is safer.

Part fourLoop until dry

Some loops have no test to pass. Finding traps is one. You cannot run a script that says "all the Python-versus-JavaScript differences have been found". For open-ended discovery, use a loop-until-dry stop condition: keep running discovery rounds until a set number of rounds in a row turn up nothing new, with a hard cap on rounds as a backstop.

For Kestrel, a round is four cheap agents, each scanning a quarter of kestrel/ for semantics that differ between the languages and are not yet in MIGRATION.md's Known traps. A single writer merges what they find. The run stops after two consecutive dry rounds or five rounds total. Here is what a run might look like (illustrative):

round 14 scanners · 3 new traps: banker's rounding (T1), negative modulo (T3), default sort order (T4)
round 24 scanners · 2 new: floor division (T2), PPM header comments (T5)
round 34 scanners · 0 new (1 duplicate of T1 rejected by the writer)
round 44 scanners · 0 new
stoptwo dry rounds in a row · 5 traps recorded · 16 scanner agents used

Two dry rounds instead of one, because one quiet round is often luck. A cap, because "until dry" with no cap is a runaway waiting to happen. And a single writer, because four scanners appending to the same file at once is the Lesson 12 conflict all over again.

Part fiveBudgets and the kill switch

Every loop needs a ceiling on spend, and at scale you want ceilings at several levels.

  • Per agent. A turn cap. In headless runs, --max-turns. For a named subagent, the maxTurns frontmatter field; a workflow can start that subagent by name with agent(..., { agentType }).
  • Per headless run. --max-budget-usd. It is a client-side estimate and can overshoot by one step, so set it a little below what you can afford.
  • Per workflow. budget.total and budget.remaining(). Check them at wave boundaries, where stopping leaves the repo in a clean state.
  • By hand. In /workflows, p pauses and x stops. In the main session, Esc interrupts. A runaway looks like rising turns and cost with no new green modules; stop it, read why, rerun.

What you should see

On the sabotaged run, three canaries start and the log reports a tripped breaker naming image.ts, with about eleven modules never started. Canaries that report failed rather than blocked get up to two retries each, so you may count up to nine port agents; that is still far fewer than 14 porters each burning a full budget. git diff on image.ts should show only your sabotage. On the second run the canaries pass, the breaker stays closed, and the full wave runs.

Stretch

Ask Claude for a loop-until-dry workflow: each round, four haiku agents scan a quarter of kestrel/ for Python-versus-JavaScript differences missing from MIGRATION.md; one writer agent merges new ones; stop after two consecutive rounds with nothing new or five rounds total. Compare what it finds with the traps your porters reported.

Key takeaway

At scale, design for failure as the normal case. Retry only with new information and only up to a cap, make every step safe to repeat, and let a canary and a breaker stop correlated failure before it spends the whole wave's budget.
