Lesson 19 Week 4 · Scale ~16 min 100 agents

Tracing, cost, and when 100 is worse than 10

More agents buy wall-clock time. They pay for it in tokens, coordination and risk, and past a certain point they stop buying anything at all. This lesson gives you a cost model, runs the whole starter with a fleet so you have real numbers, and extrapolates to 240 modules without pretending to more precision than you have.

Part oneTrace every node

A trace is a record of what each node in your graph did: which module, which model, how many attempts, what status, and roughly what it cost. Without one, a fleet run is a black box that turns money into a mix of green and red. With one, you can answer the questions that matter. Which modules are expensive? Do retries cluster in one package? Did the breaker trip on an upstream cause or on noise?

You already have most of the pieces. The workflow's schema results give you module, status and attempts per agent. /workflows shows the live shape and labels. /usage shows what the session has spent, and for headless runs the JSON output carries total_cost_usd and num_turns per run (Lesson 12). And scripts/status.py is the ground truth for what actually works. The lab's workflow puts these together: it logs per-wave tallies and verify-run counts, and you read the session cost before and after.

Divide the cost by the modules that came out green, and you get the single most useful number in this lesson: cost per green module. It folds in retries, verify agents and wasted attempts, because all of them were spent to get those modules over the line.

Part twoA cost model and a time model

Tokens are cost, so a fleet's cost is mostly its token count. A useful approximation for a migration:

total cost ≈ (cost per green module × modules) + coordination + waste

Coordination is everything that is not porting: scout agents, sub-leads, integrators, reviewers, the difftest gate. Waste is work you threw away: ports on a broken dependency, duplicate work after a non-idempotent rerun, runaways. Anthropic's research post measured agents using about 4x the tokens of a chat, and multi-agent systems about 15x. It also found that token usage alone explained about 80% of the performance differences on their browsing eval. In research, more tokens often bought better answers. In porting, the bar is a test that either passes or fails. Tokens spent after a module is green buy nothing.

Time behaves differently. Each wave of the dependency graph is a barrier, because wave L4 cannot start until L3's modules exist. Within a wave, N agents work through the modules in rounds. So the number of rounds is the sum, over waves, of the wave size divided by N, rounded up. When N is at least as large as the widest wave, every wave takes one round, and you hit a floor: the number of waves. This is Amdahl's law in migration form. The part of the work that must happen in sequence sets a limit that no number of agents can beat.

The full Kestrel library has about 240 modules in 7 waves. To make the arithmetic concrete, assume the story's waves hold 4, 10, 6, 140, 50, 20 and 10 modules. That split is illustrative; the 7 waves and the wide middle wave are the real shape.

Predict first

Using the figure, how much faster does the 240-module migration get when you go from 25 agents to 100? Four times the agents: is it four times faster?

The answer

Rounds drop from 13 to 8, so at best about 1.6x faster for 4x the agents. Five of the seven waves already finish in one round at 25 agents, so extra agents only help L3 and L4. And that 1.6x assumes each round takes the same time at 100 agents as at 25, which it will not: more parallel writers means more conflicts for the integrator, more agents running test suites on the same machine, and more correlated failures when one rule in MIGRATION.md is wrong. The real gain is smaller, and it can go negative.

Part threeThe coordination tax

Each extra agent adds a little work that is not porting. At 10 agents you barely notice it. At 100 it is a line item. These are the costs that grow with N on Kestrel:

  • Merge and integration. More modules land at once, so the integrator regenerates the barrel and resolves more overlaps per round. With worktrees, each agent's branch also has to be merged.
  • Reading load. More reports per round means more sub-leads, and each sub-lead is another agent's worth of tokens (Lesson 17).
  • Blast radius. A wrong instruction in MIGRATION.md runs once per agent. At 100 agents a bad rule is wrong 100 times before anyone looks.
  • Machine and account limits. Every port ends with scripts/verify.sh, which runs pytest and vitest. A hundred of those at once on one laptop slows every one of them, and you are more likely to hit your account's rate limits.
  • Communication. If agents talk to each other directly, channels grow as n(n−1)/2. That is 45 for 10 agents and 4,950 for 100 (Lesson 13). Hub-and-spoke and trees exist to avoid this.
  • Human review. The difftest gate and your sign-off do not get faster with more agents. A bigger batch of changes arrives at them all at once.

Workflows run 16 agents at once by default (CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS, adjustable from 1 to 256). For Kestrel that is a sensible place to sit. The starter's widest wave is 14, so 16 never waits. In the full library, 16 turns the 140-module wave into 9 rounds and the whole run into 19, against 13 rounds at 25 agents, and it does so with noticeably less tax. Raise it only after you have watched a run at 16 and know what each round really costs.

Try the trade-off yourself. Drag the agent count and watch wall-clock and cost move against each other.

Part fourAn honest extrapolation

Here is the model applied to 240 modules. Two inputs are placeholders until you run the lab: about $0.25 per green module and about 6 minutes per round. Both are illustrative. The coordination overhead percentages are judgment calls based on the list above, not measurements. Treat every figure in this table as an estimate and replace the inputs with your own numbers.

Estimates from an illustrative model: 240 modules × $0.25, 6 minutes per round, the wave split above. The shape is the lesson: cost rises slowly, time falls fast and then flattens.

Read the table from the top. Going from 1 to 10 agents cuts wall-clock by roughly ten times for a small rise in cost. That is an easy decision. Going from 10 to 25 still saves over an hour. Going from 25 to 100 saves perhaps half an hour on paper, costs noticeably more, and carries real risk that slower rounds eat the saving. For most teams, 100 agents is worse than 25, unless a deadline makes half an hour worth a lot.

Make the call

Your lead asks whether to run Kestrel-240 with 25 agents or 100.

The situation
  1. The target is "done by Friday", and it is Tuesday.
  2. Your Lab 19 numbers match the table's inputs closely.
  3. The run happens on one workstation under one account.
  4. One person will review the difftest results and sign off.

Decide, then see the reasoning.

Right call

An estimated 1.3 hours against a three-day deadline leaves room for two or three full reruns. One workstation running 100 test suites at once would slow each round, and the single reviewer is the real bottleneck either way.

Not quite

The best case saves about half an hour, which the deadline does not need. You would pay more for coordination, raise the blast radius of any bad rule, and likely lose the saving to slower rounds on one machine.

Lab 19 · In Claude Code ~30 min · est. $3–$8

Goal. Port all 24 starter modules with a fleet of cheap workers, measure cost per green module and wall-clock, then extrapolate to 240 modules at 10, 25 and 100 agents.

  1. Reset the port in kestrel-scale/.

    cd kestrel-scale
git add -A && git commit -qm "before lab 19" --allow-empty
git rm -rq --ignore-unmatch ts/src ts/test && git checkout fresh -- ts

  2. Create the workflow. It loops over waves until status.py has nothing ready, with a no-progress check, a wave cap and a breaker.

    export const meta = {
  name: 'port-all',
  description: 'Port every remaining starter module wave by wave until status.py has nothing ready',
  phases: [{ title: 'Waves' }, { title: 'Tally' }]
}

const MAX_WAVES = 8
const BREAKER = 0.3
const listSchema = { type: 'object', properties: { modules: { type: 'array', items: { type: 'string' } } }, required: ['modules'] }
const resultSchema = {
  type: 'object',
  properties: {
    module: { type: 'string' },
    status: { type: 'string', enum: ['passed', 'failed', 'skipped', 'blocked'] },
    attempts: { type: 'integer', description: 'How many times you ran scripts/verify.sh' }
  },
  required: ['module', 'status', 'attempts']
}

const port = (m) => agent(
  `Port ${m} and its tests to TypeScript per MIGRATION.md. If python scripts/status.py --json shows it passing, return "skipped".
Port every Python test as it("test_name"). Edit only this module's files under ts/src and ts/test; never ts/src/index.ts, MIGRATION.md or a dependency.
If a dependency looks broken, return "blocked". You are done only when scripts/verify.sh ${m} exits 0.
Run verify.sh at most 3 times; after a failure, read the output before editing again.`,
  { label: `port ${m}`, model: 'haiku', schema: resultSchema })

phase('Waves')
const all = []
let lastKey = ''
let stopped = 'dry: nothing left to port'
for (let w = 1; w <= MAX_WAVES; w++) {
  const ready = (await agent('Run python scripts/status.py --next. Return the module ids it prints, like ops/blur. Edit nothing.',
    { label: `find wave ${w}`, model: 'haiku', schema: listSchema }))?.modules ?? []
  const key = ready.slice().sort().join(',')
  if (ready.length === 0) break
  if (key === lastKey) { stopped = `no progress: wave ${w} is the same set as wave ${w - 1}`; break }
  lastKey = key
  const results = (await parallel(ready.map((m) => () => port(m)))).filter(Boolean)
  all.push(...results)
  const red = results.filter((r) => r.status === 'failed' || r.status === 'blocked').length
  log(`Wave ${w}: ${ready.length} ready, ${results.length - red} green, ${red} red`)
  if (red / Math.max(results.length, 1) > BREAKER) { stopped = `breaker tripped in wave ${w}`; break }
  if (w === MAX_WAVES) stopped = 'wave cap reached'
}

phase('Tally')
await agent('Run python scripts/gen_barrel.py to regenerate ts/src/index.ts. Edit nothing else.', { label: 'regenerate barrel', model: 'haiku' })
const runs = all.reduce((n, r) => n + (r.attempts ?? 1), 0)
const green = all.filter((r) => r.status === 'passed').length
log(`Stopped because: ${stopped}`)
log(`${green} ported green, ${all.length - green} not green, ${runs} verify.sh runs (${(runs / Math.max(all.length, 1)).toFixed(2)} per module)`)
log('Now run /usage, note the cost, and divide by the green count for cost per module.')

  3. Start Claude Code and read the starting cost.

    CLAUDE_CODE_SUBAGENT_MODEL=haiku claude --model sonnet
    /usage

  4. In a second terminal, note the start time. Then run the workflow. Expect the "Large workflow" warning, since this run uses well over 25 agents. During the L3 wave, open /workflows and count how many porters are running at once.

    date
    /port-all

  5. When it finishes, note the end time, the cost and the final state.

    date
python scripts/status.py
    /usage

  6. Have Claude build the extrapolation from your numbers. Fill in the three blanks first.

    Write SCALE.md from my Lab 19 run.

  7. Commit the run and the analysis.

    git add -A && git commit -qm "lab 19: full starter, SCALE.md"
What you should see

Seven waves: 2, 2, 1, 14, 3, 1 and 1 modules. Most of the wall-clock goes to the narrow waves, where one or two agents work while the rest of the fleet has nothing to do. The L3 wave shows up to 14 porters at once, under the 16 default. The tally prints the verify runs per module; anything well above 1.5 points at traps worth writing into MIGRATION.md. Your SCALE.md table should have the same shape as the one in Part four, with your numbers in it.

Stretch

Reset and rerun with CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS=4 set before starting claude. Cost should come out similar; wall-clock should rise, almost all of it in L3. Add the measured point to SCALE.md and check how well your model predicted it.

Key takeaway

Agents trade money for time, and the trade gets worse as you add them. The critical path sets a floor no fleet can beat, and coordination costs rise with every agent. Measure cost per green module, model rounds per wave, and stop adding agents where the curve flattens.
